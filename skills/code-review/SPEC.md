# 质量保障报告规范

**版本**: 1.4.0
**适用范围**: 所有项目的质量保障活动（静态审查、E2E 测试、API 测试）

---

## 1. 概述

本规范定义了质量保障报告的格式标准，确保每一份报告都具备完整的问题描述、可复现的证据链和可追溯的根因分析。

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| 事实驱动 | 没有证据的 Bug 报告是观点，不是事实 |
| 根因导向 | AI Agent 的独特价值在于发现问题的同时完成根因定位 |
| 可复现性 | 任何人按照报告步骤操作，必须能复现问题 |
| 生命周期完整 | 每个问题从发现到关闭，状态流转清晰可追溯 |

### 1.2 活动类型

质量保障体系覆盖三类活动，共享同一套严重程度定义和生命周期状态：

| 活动类型 | 编号前缀 | 触发时机 | 产出物 |
|----------|---------|---------|--------|
| 静态代码审查 | CR-xxx | 代码变更时 | 代码问题清单 |
| E2E 界面测试 | E2E-xxx | 功能开发完成时 | 交互 Bug 报告 |
| API 接口测试 | API-xxx | 接口变更时 | 接口异常报告 |

---

## 2. Bug 报告 5 要素

**每份 Bug 报告必须回答以下 5 个问题，缺一不可：**

| 序号 | 要素 | 问题 | 说明 |
|------|------|------|------|
| 1 | 定位 | 在哪发现的？ | 环境 + 页面 + 组件精确定位 |
| 2 | 复现 | 怎么触发的？ | 可复现的操作步骤，编号列出 |
| 3 | 期望 | 期望什么？ | 需求/设计定义的正确行为 |
| 4 | 实际 | 实际怎样？ | 偏离期望的具体表现 |
| 5 | 根因 | 为什么会这样？ | 源码级根因追溯（AI Agent 独特优势） |

### 2.1 为什么需要第 5 要素

传统 QA 流程中，测试人员负责前 4 要素，开发人员负责根因定位。AI Agent 同时具备测试能力和代码阅读能力，可以在发现 Bug 的同时完成根因定位，极大缩短修复周期。

**根因追溯的标准格式：**

```markdown
**为什么会出现这个问题？**

1. **直接原因**：[描述触发问题的直接代码逻辑]
2. **源码定位**：`文件路径:行号` - [关键代码片段]
3. **深层原因**：[为什么代码会写成这样 -- 设计缺陷/遗漏/误解]
```

---

## 3. 严重程度定义

| 等级 | 标记 | 定义 | 判断标准 |
|------|------|------|----------|
| 阻塞 | **[阻塞]** | 功能完全不可用 | 核心流程中断，无法绕过 |
| 高 | **[高]** | 功能严重受损 | 核心流程受影响，但有临时绕过方案 |
| 中 | **[中]** | 功能部分异常 | 非核心流程受影响，或有明显性能/安全隐患 |
| 低 | **[低]** | 体验或规范问题 | UI 瑕疵、文案错误、代码规范问题 |

---

## 4. 生命周期状态

```
发现 --> 待确认 --> 已确认 --> 修复中 --> 已修复 --> 已验证 --> 已关闭
                      |                              |
                   不是Bug --> 已关闭(非问题)      验证失败 --> 已确认(重新修复)
```

| 状态 | 说明 |
|------|------|
| 待确认 | 已记录，等待确认是否为真实问题 |
| 已确认 | 确认为真实问题，等待修复 |
| 修复中 | 正在修复 |
| 已修复 | 修复完成，等待验证 |
| 已验证 | 验证通过 |
| 已关闭 | 问题已解决或判定为非问题 |

## 5. 证据链要求

### 5.1 证据类型

| 证据类型 | 采集方式 | 适用活动 | 必要性 |
|----------|---------|---------|--------|
| 页面快照（a11y tree） | Chrome MCP take_snapshot | E2E | 必需 |
| 屏幕截图 | Chrome MCP take_screenshot | E2E | 必需 |
| 网络请求/响应 | Chrome MCP list_network_requests + get_network_request | E2E, API | 必需 |
| 控制台日志 | Chrome MCP list_console_messages | E2E | 按需 |
| 源码片段 | auggie-mcp Skill + view | CR, E2E, API | 必需（根因追溯时） |
| API 请求/响应体 | Chrome MCP 或 HTTP 客户端 | API | 必需 |

### 5.2 证据引用格式

```markdown
**页面快照**：[snapshot-001](./evidence/snapshot-001.txt)
**截图**：[screenshot-001](./evidence/screenshot-001.png)
**网络请求**：reqid #42, POST /api/hazards/detected, 状态码 422
**源码定位**：`app/services/hazard_service.py:45-52`
```

## 6. 报告文件规范

### 6.1 文件命名

```
docs/code-review/YYYY-MM-DD-{scope}.md
```

| 字段 | 说明 | 示例 |
|------|------|------|
| YYYY-MM-DD | 测试日期 | 2026-02-12 |
| scope | 测试范围（功能模块/页面名称） | hazard-audit, clause-detail |

### 6.2 报告头部模板

```markdown
# {范围} 质量保障报告

## 报告信息

| 项目 | 内容 |
|------|------|
| 报告日期 | YYYY年MM月DD日 HH:MM:SS |
| 活动类型 | 静态代码审查 / E2E 界面测试 / API 接口测试 |
| 覆盖范围 | {变更文件、页面、接口或功能模块} |
| 执行方式 | 主 AI 助手 / 主 AI 助手 + 子代理 / Chrome MCP + AI Agent / HTTP 客户端 |
| 环境或基线 | {分支、commit、服务地址、测试环境，按活动类型填写} |
| 报告状态 | 进行中 / 已完成 |
```

活动特有字段按需补充：静态代码审查可补充分支、diff 范围和 reviewer；E2E/API 可补充前端地址、后端地址、浏览器环境和账号角色。

### 6.3 问题条目模板

```markdown
### {编号}: {问题标题} [{严重程度}]

**发现位置**：{文件路径/接口/页面/组件}
**发现时间**：YYYY年MM月DD日 HH:MM:SS
**状态**：待确认 / 已确认 / 已修复 / 已验证 / 已关闭

#### 1. 在哪发现的

| 项目 | 内容 |
|------|------|
| 定位类型 | 文件路径 / API 端点 / 页面路径 |
| 具体位置 | {文件:行号 / METHOD URL / 页面 > 组件} |
| 关联范围 | {调用链、配置、测试、按钮或输入参数} |

#### 2. 怎么触发的

{静态代码审查填写调用链或变更触发条件；E2E/API 填写可复现操作步骤或请求参数。}

#### 3. 期望什么

{描述需求、设计原则、接口契约或最佳实践定义的正确行为}

#### 4. 实际怎样

{描述偏离期望的具体表现、代码实现或响应结果}

**证据：**
- 源码定位：`{文件路径}:{行号}`
- 截图：[screenshot-xxx](./evidence/screenshot-xxx.png)（如有）
- 网络请求：reqid #xx, {METHOD} {URL}, 状态码 {code}（如有）
- 控制台：{错误信息}（如有）
- 辅助审查结论：{子代理/人工 reviewer/外部工具结论摘要，如有}

#### 5. 为什么会这样

1. **直接原因**：{描述}
2. **源码定位**：`{文件路径}:{行号}`
   ```{language}
   {关键代码片段}
   ```
3. **深层原因**：{为什么代码会写成这样}

#### 修复建议

{具体的修复方案，包含代码示例}
```

### 6.4 辅助审查产物归档（可选）

当使用子代理、人工 reviewer 或外部审查工具辅助静态审查时，必须保存可追溯的结论摘要：

| 产物类型 | 路径规范 | 约束 |
|----------|----------|------|
| 辅助审查输入 | 可选，按项目约定归档 | 记录审查范围、目标和限制条件 |
| 辅助审查结论 | 可选，按项目约定归档 | 作为参考证据，必须由主 AI 助手复核后采纳 |
| 失败或降级记录 | `docs/code-review/YYYY-MM-DD-{scope}.md` 内说明 | 辅助 reviewer 不可用时必须说明降级范围 |
| 最终报告 | `docs/code-review/YYYY-MM-DD-{scope}.md` | 面向评审与归档的正式报告 |

**执行校验要求**：

1. 主 AI 助手必须完成最终审查判断，不得直接把辅助结论当作最终报告。
2. 辅助结论必须去重、分级，并标注是否阻塞交付。
3. 辅助 reviewer 不可用、输出为空或不可解释时，不得跳过审查；必须降级为主 AI 助手直接审查。
4. 最终报告必须注明实际采用的审查方式、覆盖范围和剩余风险。

## 8. 三类活动的差异化要求

### 8.1 静态代码审查（CR-xxx）

CR 类报告的 5 要素适配：

| 要素 | CR 语境下的含义 |
|------|----------------|
| 定位 | 文件路径 + 行号范围 |
| 复现 | 代码调用链追溯（而非操作步骤） |
| 期望 | 代码应遵循的设计原则或最佳实践 |
| 实际 | 代码的实际实现方式 |
| 根因 | 为什么代码会偏离最佳实践 |

### 8.2 E2E 界面测试（E2E-xxx）

E2E 类报告的证据链要求最严格：

| 证据 | 必要性 | 说明 |
|------|--------|------|
| 页面快照 | 必需 | 证明 UI 状态 |
| 截图 | 必需 | 视觉证据 |
| 网络请求 | 必需 | 前后端交互证据 |
| 控制台日志 | 按需 | 运行时错误 |
| 源码追溯 | 必需 | 根因定位 |

### 8.3 API 接口测试（API-xxx）

API 类报告的 5 要素适配：

| 要素 | API 语境下的含义 |
|------|-----------------|
| 定位 | API 端点（METHOD + URL） |
| 复现 | 请求参数（Headers + Body） |
| 期望 | API 文档定义的响应格式和状态码 |
| 实际 | 实际响应（状态码 + Body） |
| 根因 | 后端处理逻辑的问题定位 |
