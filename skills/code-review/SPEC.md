# 质量保障报告规范

**版本**: 1.3.0
**适用范围**: 所有项目的质量保障活动（静态审查、E2E 测试、API 测试）

---

## 1. 概述

本规范定义了质量保障报告的格式标准，确保每一份报告都具备完整的问题描述、可复现的证据链和可追溯的根因分析。

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| 事实驱动 | 没有证据的 Bug 报告是观点，不是事实 |
| 根因导向 | AI Agent 的独特价值在于发现问题的同时完成根因定位 |
| 可复现性 | 任何人按照报告步骤操作，必须能复现问题 |
| 生命周期完整 | 每个问题从发现到关闭，状态流转清晰可追溯 |

### 1.2 活动类型

质量保障体系覆盖三类活动，共享同一套严重程度定义和生命周期状态：

| 活动类型 | 编号前缀 | 触发时机 | 产出物 |
|----------|---------|---------|--------|
| 静态代码审查 | CR-xxx | 代码变更时 | 代码问题清单 |
| E2E 界面测试 | E2E-xxx | 功能开发完成时 | 交互 Bug 报告 |
| API 接口测试 | API-xxx | 接口变更时 | 接口异常报告 |

---

## 2. Bug 报告 5 要素

**每份 Bug 报告必须回答以下 5 个问题，缺一不可：**

| 序号 | 要素 | 问题 | 说明 |
|------|------|------|------|
| 1 | 定位 | 在哪发现的？ | 环境 + 页面 + 组件精确定位 |
| 2 | 复现 | 怎么触发的？ | 可复现的操作步骤，编号列出 |
| 3 | 期望 | 期望什么？ | 需求/设计定义的正确行为 |
| 4 | 实际 | 实际怎样？ | 偏离期望的具体表现 |
| 5 | 根因 | 为什么会这样？ | 源码级根因追溯（AI Agent 独特优势） |

### 2.1 为什么需要第 5 要素

传统 QA 流程中，测试人员负责前 4 要素，开发人员负责根因定位。AI Agent 同时具备测试能力和代码阅读能力，可以在发现 Bug 的同时完成根因定位，极大缩短修复周期。

**根因追溯的标准格式：**

```markdown
**为什么会出现这个问题？**

1. **直接原因**：[描述触发问题的直接代码逻辑]
2. **源码定位**：`文件路径:行号` - [关键代码片段]
3. **深层原因**：[为什么代码会写成这样 -- 设计缺陷/遗漏/误解]
```

## 3. 严重程度定义

| 等级 | 标记 | 定义 | 判断标准 |
|------|------|------|----------|
| 阻塞 | **[阻塞]** | 功能完全不可用 | 核心流程中断，无法绕过 |
| 高 | **[高]** | 功能严重受损 | 核心流程受影响，但有临时绕过方案 |
| 中 | **[中]** | 功能部分异常 | 非核心流程受影响，或有明显性能/安全隐患 |
| 低 | **[低]** | 体验或规范问题 | UI 瑕疵、文案错误、代码规范问题 |

---

## 4. 生命周期状态

```
发现 --> 待确认 --> 已确认 --> 修复中 --> 已修复 --> 已验证 --> 已关闭
                      |                              |
                   不是Bug --> 已关闭(非问题)      验证失败 --> 已确认(重新修复)
```

| 状态 | 说明 |
|------|------|
| 待确认 | 已记录，等待确认是否为真实问题 |
| 已确认 | 确认为真实问题，等待修复 |
| 修复中 | 正在修复 |
| 已修复 | 修复完成，等待验证 |
| 已验证 | 验证通过 |
| 已关闭 | 问题已解决或判定为非问题 |

## 5. 证据链要求

### 5.1 证据类型

| 证据类型 | 采集方式 | 适用活动 | 必要性 |
|----------|---------|---------|--------|
| 页面快照（a11y tree） | Chrome MCP take_snapshot | E2E | 必需 |
| 屏幕截图 | Chrome MCP take_screenshot | E2E | 必需 |
| 网络请求/响应 | Chrome MCP list_network_requests + get_network_request | E2E, API | 必需 |
| 控制台日志 | Chrome MCP list_console_messages | E2E | 按需 |
| 源码片段 | Augment Codebase + view | CR, E2E, API | 必需（根因追溯时） |
| API 请求/响应体 | Chrome MCP 或 HTTP 客户端 | API | 必需 |

### 5.2 证据引用格式

```markdown
**页面快照**：[snapshot-001](./evidence/snapshot-001.txt)
**截图**：[screenshot-001](./evidence/screenshot-001.png)
**网络请求**：reqid #42, POST /api/hazards/detected, 状态码 422
**源码定位**：`app/services/hazard_service.py:45-52`
```

| scope | 测试范围（功能模块/页面名称） | hazard-audit, clause-detail |

### 6.4 Codex 审查产物归档

当使用 Codex CLI 辅助静态审查时，必须保存完整执行链路：

| 产物类型 | 路径规范 | 约束 |
|----------|----------|------|
| Prompt 输入 | `docs/code-review/_inputs/*.prompt.md` | 禁止只在命令行内联长 Prompt |
| 原始输出 | `docs/code-review/_codex_raw/*.md` | 作为可追溯原始证据，必须保留 |
| 失败记录 | `docs/code-review/_codex_failures/*.md` | 执行失败时必须生成 |
| 最终报告 | `docs/code-review/YYYY-MM-DD-{scope}.md` | 面向评审与归档的正式报告 |

**执行校验要求**：

1. 命令退出码必须为 `0`。
2. 原始输出文件必须存在且非空。
3. 失败时至少重试一次，并保留失败记录文件路径。
4. 若存在流式日志但最终超时，不得标记为“无输出”；必须标记为“部分输出失败”并记录 `session_id`（如可提取），可通过 `codex exec resume <session_id> - < <prompt_file>` 恢复。
5. 若外层调用器存在独立等待超时（如 `launch-process.max_wait_seconds`），必须满足：外层超时 >= wrapper `--timeout + 30s`，避免外层先结束导致失败记录缺失。
6. 连续 2 次网络型失败（`failure_type=timeout_with_partial_stream_output` / `network_unstable_after_retries` 或日志含 `reconnect`）时，必须降级为人工审查并在最终报告注明“网络不可达降级”。

## 8. 三类活动的差异化要求

### 8.1 静态代码审查（CR-xxx）

CR 类报告的 5 要素适配：

| 要素 | CR 语境下的含义 |
|------|----------------|
| 定位 | 文件路径 + 行号范围 |
| 复现 | 代码调用链追溯（而非操作步骤） |
| 期望 | 代码应遵循的设计原则或最佳实践 |
| 实际 | 代码的实际实现方式 |
| 根因 | 为什么代码会偏离最佳实践 |

### 8.2 E2E 界面测试（E2E-xxx）

E2E 类报告的证据链要求最严格：

| 证据 | 必要性 | 说明 |
|------|--------|------|
| 页面快照 | 必需 | 证明 UI 状态 |
| 截图 | 必需 | 视觉证据 |
| 网络请求 | 必需 | 前后端交互证据 |
| 控制台日志 | 按需 | 运行时错误 |
| 源码追溯 | 必需 | 根因定位 |

### 8.3 API 接口测试（API-xxx）

API 类报告的 5 要素适配：

| 要素 | API 语境下的含义 |
|------|-----------------|
| 定位 | API 端点（METHOD + URL） |
| 复现 | 请求参数（Headers + Body） |
| 期望 | API 文档定义的响应格式和状态码 |
| 实际 | 实际响应（状态码 + Body） |
| 根因 | 后端处理逻辑的问题定位 |
