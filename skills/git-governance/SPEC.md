# Git 协作治理规范

**版本**: 1.1.0
**适用范围**: 共享分支协作、双端开发同步、含大体量数据目录的仓库

---

## 1. 概述

本规范定义 Git 协作中的统一决策标准、执行流程和证据记录要求，目标是降低以下风险：

- 历史被意外改写（rebase/force push）
- 大文件差异重放导致超时或中断
- 多端并发提交造成长期分叉
- 问题处置不可追溯、不可回滚

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| 可回滚优先 | 高风险操作前必须保留可回退锚点 |
| 共享分支稳定优先 | 默认选择 merge，避免改写已共享历史 |
| 证据先行 | 决策前先采集客观状态，不凭记忆操作 |
| 最小意外原则 | 日常同步禁止隐式 merge |

---

## 2. 术语定义

| 术语 | 定义 |
|------|------|
| 共享分支 | 有多人或多环境持续提交的远端分支（如 `feature/shared`） |
| 高风险操作 | rebase、merge、reset、force push、跨端并发整合 |
| 救援分支 | 风险操作前创建的 `rescue/<timestamp>` 保护分支 |
| 大体量数据目录 | 体积大、变更多、重放代价高的目录（如 `vector_db/`） |
| 双端开发 | 同一人使用 WSL + Remote SSH（或类似）并行开发 |

---

## 3. 策略矩阵

### 3.1 操作级策略

| 操作 | 默认策略 | 允许条件 | 禁止条件 |
|------|----------|----------|----------|
| `git pull` | 必须使用 `--ff-only` | 本地线性可快进 | 直接裸用 `git pull` |
| `merge` | 共享分支默认允许 | 已完成基线采集并创建救援分支 | 未看清差异直接合并 |
| `rebase` | 共享分支默认禁止 | 仅本地未共享分支，且用户明确授权 | 含大体量数据目录或已共享提交 |
| `push --force` | 默认禁止 | 用户明确授权、范围明确、可回滚锚点已建立 | 未经确认直接强推 |
| `reset --hard` | 默认禁止 | 用户明确授权且无需保留工作区 | 常规冲突处理场景 |

### 3.2 场景级策略

| 场景 | 目标 | 标准动作 |
|------|------|----------|
| 日常开始开发 | 保持线性同步 | `fetch` -> `pull --ff-only` |
| push 被拒绝 | 稳定整合远端新增提交 | `fetch` -> 建救援分支 -> `merge` -> `push` |
| rebase 异常 | 快速回到可解释状态 | `rebase --abort` -> 走 merge 路径 |
| 双端同步 | 防止双端互拉分叉 | 单向主端提交，副端仅同步 |

---

## 4. 标准流程

### 4.1 日常同步流程

```bash
git fetch origin
git pull --ff-only origin <branch>
```

失败处理：若 `--ff-only` 失败，进入 4.2 流程。

### 4.2 Push 被拒绝处理流程（non-fast-forward）

```bash
git fetch origin
git branch rescue/<timestamp>
git merge origin/<branch>
git push origin <branch>
```

执行要求：

1. merge 前必须确认当前不在 rebase 中间态。
2. merge 后必须检查 `status` 为干净或仅剩预期变更。
3. 禁止用强推替代常规整合。

### 4.3 Rebase 异常恢复流程

```bash
git status
git rebase --abort
git fetch origin
git branch rescue/<timestamp>
git merge origin/<branch>
```

执行要求：

1. 如已 detached HEAD，先记录当前提交哈希。
2. `abort` 后确认回到目标分支再继续。

### 4.4 双端开发流程（WSL + Remote SSH）

- 主端（建议 WSL）：`pull --ff-only` -> 开发/提交 -> `push`
- 副端（建议 SSH）：仅同步主端结果，不并发提交同一任务
- 副端若有本地改动：先 `stash`，同步后 `stash pop`

约束：

- 禁止两端分别先提交后再互拉。
- 若已出现双端分叉，回到主端统一整合。

## 5. 证据采集与记录要求

### 5.1 基线命令（必采）

```bash
git status -sb
git branch -vv
git log --oneline --decorate -n 20
git remote -v
```

### 5.2 决策记录最小字段

每次触发治理流程，至少记录以下字段到工作日志：

| 字段 | 说明 |
|------|------|
| 触发场景 | 例如 `push 被拒绝`、`rebase 中断` |
| 现场状态 | 分支状态、是否分叉、是否存在大体量目录变更 |
| 采取动作 | 具体命令链（merge / abort / rescue 分支） |
| 决策理由 | 为什么选该方案，为什么不选替代方案 |
| 结果状态 | 是否成功推送，是否与远端对齐 |

### 5.3 记录模板

```markdown
## Git 协作治理记录

- 触发场景：
- 现场状态：
- 采取动作：
- 决策理由：
- 结果状态：
- 关联分支与提交：
```

---

## 6. 禁止清单

以下行为默认禁止：

1. 在共享分支直接执行 rebase 并推送重写历史。
2. 未建立救援分支即进行高风险整合。
3. 以 `push --force` 替代标准冲突整合流程。
4. 忽略大体量数据目录对整合耗时和失败率的影响。
5. 双端并发提交后再尝试互拉自愈。

---

## 7. 例外审批

若必须偏离本规范（如历史清理、强推、非常规回滚），需满足：

1. 用户明确授权偏离动作和影响范围。
2. 已建立可回滚锚点（救援分支或标签）。
3. 在工作日志中记录偏离原因与恢复路径。

---

## 8. 验收清单

执行完成后，至少满足：

1. 本地分支与远端目标分支同步（无未预期分叉）。
2. 工作区状态可解释（干净或仅剩预期变更）。
3. 未使用未授权的破坏性操作。
4. 工作日志已记录“触发-决策-结果”闭环。

---

## 9. 标准提交信息规范

### 9.1 目标

本节定义项目内统一的 Git 提交信息格式，确保每个提交都能独立说明“为什么改、改了什么、影响和边界是什么”，而不是只留下一个无法审计的一行摘要。

为什么：提交历史是代码审查、事故回溯、版本发布和跨 Agent 交接的长期事实源。AI 生成提交信息时如果只描述表面 diff，后续维护者无法判断背景、决策边界、兼容影响和后续风险。

### 9.2 适用范围

本规范适用于本项目内所有由 AI 发起、代写、建议或执行的提交；开发者手工提交也应遵循本规范。

不再区分“计划型提交”和“日常零散提交”。只要提交进入项目历史，就必须满足本节要求。

### 9.3 标题格式

提交标题必须采用 Conventional Commits 风格：

```text
<type>(<scope>): <中文摘要>
```

标题要求：

| 字段 | 要求 | 示例 |
|------|------|------|
| `type` | 使用小写类型，必须能反映变更性质 | `feat`、`fix`、`docs`、`refactor` |
| `scope` | 标注受影响模块；无明确模块时可省略 | `git-governance`、`chrome-cdp` |
| 中文摘要 | 用一句话说明本次提交达成的结果，不以句号结尾 | `规范 AI 提交信息` |

允许的 `type`：

| type | 使用场景 |
|------|----------|
| `feat` | 新功能、新能力、新接口 |
| `fix` | 缺陷修复、回归修复 |
| `docs` | 文档、注释、说明材料 |
| `style` | 格式调整，不改变行为 |
| `refactor` | 重构，不新增能力也不修复缺陷 |
| `perf` | 性能优化 |
| `test` | 测试相关变更 |
| `build` | 构建系统、依赖、打包配置 |
| `ci` | CI/CD 配置与流水线 |
| `chore` | 维护性变更、工具脚本、仓库治理 |
| `revert` | 回滚提交 |

破坏性变更必须在标题中使用 `!` 或在 footer 中写明 `BREAKING CHANGE:`。

### 9.4 Body 强制要求

所有提交都必须包含 body，标题与 body 之间必须保留一个空行。

body 必须包含以下三个段落，且每段至少一条有效说明：

```text
背景：
- 当前问题、业务目标、技术约束或决策来源。

变更：
- 本次提交实际修改了什么，按影响面概括，不机械复述 diff。

影响与边界：
- 行为变化、兼容性/迁移影响、风险、限制或本次未覆盖范围。
```

要求：

1. `背景` 必须解释问题、目标、约束或决策原因。
2. `变更` 必须概括主要修改点和影响范围。
3. `影响与边界` 必须说明行为变化、兼容性/迁移影响、风险、限制或本次未覆盖范围；不适用时也要明确写 `无`。
4. 验证证据不作为 body 固定段落；验证仍属于开发闭环要求，应记录在工作日志、PR、最终回复或 `Tests:` footer 中。
5. body 不得只重复标题，不得写“见 diff”“已修改”“已验证”等空泛描述。
6. task 编号、issue、PR、ADR、SPEC 章节等追踪信息放在 body 或 footer，不再放在标题最前面。

### 9.5 Footer 规则

footer 用于记录机器可解析或跨系统追踪信息，可按需包含：

```text
Refs: #123
Closes: #456
Task: task-3
Spec: docs/development/2026-04-29-git-message.md
Tests: go test ./...
BREAKING CHANGE: 移除旧提交格式兼容要求
```

footer 与 body 之间必须保留一个空行。

### 9.6 AI 生成提交前检查

AI 生成或执行提交前，必须完成以下检查：

1. 运行 `git status -sb`，确认只包含本次任务预期文件。
2. 运行 `git diff --cached` 审查已暂存内容；若尚未暂存，则先审查 `git diff` 并只暂存本次任务文件。
3. 完成 AGENTS.md `GATE-PUBLICITY`「AI 提交前公开性自检 4 问」（细化清单见本规范 §9.6.1）。
4. 确认没有用户未授权改动、调试残留、无关格式化或被误暂存的临时文件。
5. 确认与改动匹配的验证已经执行，并记录在开发闭环；如需进入提交信息，写入 `Tests:` footer。
6. 基于实际 diff 生成提交信息，不得只根据聊天记忆编写。

#### 9.6.1 公开性自检执行清单

公开性自检不是抽象口号，是逐文件回答的检查表。AI 必须按以下顺序执行：

1. 列出本次提交涉及的文件清单：

   ```bash
   git diff --cached --name-status
   git diff --cached --name-only --diff-filter=A   # 仅新增文件
   git diff --cached --name-only --diff-filter=R   # 仅重命名文件
   ```

2. 对每个新增或重命名的文件，依次回答 AGENTS.md「AI 提交前公开性自检 4 问」：

   | 问题 | 不通过的处理 |
   |------|--------------|
   | 1. 该文件落在「公开性分类清单」哪一档？ | 落在「永远不得提交」一档时，立即从暂存区撤回（`git reset HEAD <file>`）并按"误提交应急"处理；落在「默认不提交」一档时暂停提交并向用户确认是否走 `!` 例外 |
   | 2. 是否在 `.gitignore` 默认忽略范围内？若已通过 `!` 例外公开，提交信息是否写明了公开原因与范围？ | 未声明公开原因时，暂停提交并补充提交信息；不得整目录放开 `docs/` 或 `tests/fixtures/` |
   | 3. 文件内容是否包含真实密钥、Token、内网 URL、客户数据或个人身份信息？是否需要脱敏？ | 检测到敏感串时，撤回暂存并改为脱敏版本；如已 push，按 AGENTS.md「误提交应急」轮转密钥并清理历史 |
   | 4. 这是测试文件吗？若是，按当前仓库公开性形态判定它属于哪一类（单元/集成/E2E/夹具/覆盖率产物）？ | 含真实数据或生产快照的测试不得进入 `public-*` 仓库；覆盖率产物在任何形态都不得入库 |

3. 对修改类（M）文件，重点检查 diff 是否新增了上一档敏感串：

   ```bash
   git diff --cached -U0 | grep -E '(api[_-]?key|secret|token|password|bearer|authorization|aws_access|private[_-]?key|-----BEGIN)' -i
   ```

   命中结果不必然是真问题（例如本次就在写防泄漏文档），但必须人工确认每条命中后才能继续。

4. 若仓库形态尚未在 AGENTS.md 中声明，按 AGENTS.md「仓库形态声明」默认按 `public-open-source` 处理，并在提交信息中提示用户尽快补齐形态声明。

任一项无法肯定通过时，必须暂停提交并向用户确认；不得在不确定状态下推送。

### 9.7 禁止格式

以下提交信息默认禁止：

```text
[task 标识] 中文摘要
update
fix
misc
WIP
work in progress
临时提交
改一下
```

禁止原因：这些格式无法表达背景、变更、影响与边界，不能支撑审计回溯。

### 9.8 标准模板

```text
docs(git-governance): 规范 AI 提交信息

背景：
- 旧规范只要求 task 标识和中文摘要，无法支撑审计回溯。

变更：
- 将提交标题升级为 Conventional Commits 风格。
- 强制 body 写清背景、变更、影响与边界。

影响与边界：
- 行为变化：AI 生成提交信息时必须输出结构化 body。
- 兼容性影响：旧 `[task 标识] 中文摘要` 格式不再允许。
- 未覆盖范围：验证证据不再作为 body 固定段落，按开发闭环或 `Tests:` footer 记录。
```
