# Git 协作治理规范

**版本**: 1.0.0
**适用范围**: 共享分支协作、双端开发同步、含大体量数据目录的仓库

---

## 1. 概述

本规范定义 Git 协作中的统一决策标准、执行流程和证据记录要求，目标是降低以下风险：

- 历史被意外改写（rebase/force push）
- 大文件差异重放导致超时或中断
- 多端并发提交造成长期分叉
- 问题处置不可追溯、不可回滚

### 1.1 设计原则

| 原则 | 说明 |
|------|------|
| 可回滚优先 | 高风险操作前必须保留可回退锚点 |
| 共享分支稳定优先 | 默认选择 merge，避免改写已共享历史 |
| 证据先行 | 决策前先采集客观状态，不凭记忆操作 |
| 最小意外原则 | 日常同步禁止隐式 merge |

---

## 2. 术语定义

| 术语 | 定义 |
|------|------|
| 共享分支 | 有多人或多环境持续提交的远端分支（如 `feature/shared`） |
| 高风险操作 | rebase、merge、reset、force push、跨端并发整合 |
| 救援分支 | 风险操作前创建的 `rescue/<timestamp>` 保护分支 |
| 大体量数据目录 | 体积大、变更多、重放代价高的目录（如 `vector_db/`） |
| 双端开发 | 同一人使用 WSL + Remote SSH（或类似）并行开发 |

---

## 3. 策略矩阵

### 3.1 操作级策略

| 操作 | 默认策略 | 允许条件 | 禁止条件 |
|------|----------|----------|----------|
| `git pull` | 必须使用 `--ff-only` | 本地线性可快进 | 直接裸用 `git pull` |
| `merge` | 共享分支默认允许 | 已完成基线采集并创建救援分支 | 未看清差异直接合并 |
| `rebase` | 共享分支默认禁止 | 仅本地未共享分支，且用户明确授权 | 含大体量数据目录或已共享提交 |
| `push --force` | 默认禁止 | 用户明确授权、范围明确、可回滚锚点已建立 | 未经确认直接强推 |
| `reset --hard` | 默认禁止 | 用户明确授权且无需保留工作区 | 常规冲突处理场景 |

### 3.2 场景级策略

| 场景 | 目标 | 标准动作 |
|------|------|----------|
| 日常开始开发 | 保持线性同步 | `fetch` -> `pull --ff-only` |
| push 被拒绝 | 稳定整合远端新增提交 | `fetch` -> 建救援分支 -> `merge` -> `push` |
| rebase 异常 | 快速回到可解释状态 | `rebase --abort` -> 走 merge 路径 |
| 双端同步 | 防止双端互拉分叉 | 单向主端提交，副端仅同步 |

---

## 4. 标准流程

### 4.1 日常同步流程

```bash
git fetch origin
git pull --ff-only origin <branch>
```

失败处理：若 `--ff-only` 失败，进入 4.2 流程。

### 4.2 Push 被拒绝处理流程（non-fast-forward）

```bash
git fetch origin
git branch rescue/<timestamp>
git merge origin/<branch>
git push origin <branch>
```

执行要求：

1. merge 前必须确认当前不在 rebase 中间态。
2. merge 后必须检查 `status` 为干净或仅剩预期变更。
3. 禁止用强推替代常规整合。

### 4.3 Rebase 异常恢复流程

```bash
git status
git rebase --abort
git fetch origin
git branch rescue/<timestamp>
git merge origin/<branch>
```

执行要求：

1. 如已 detached HEAD，先记录当前提交哈希。
2. `abort` 后确认回到目标分支再继续。

### 4.4 双端开发流程（WSL + Remote SSH）

- 主端（建议 WSL）：`pull --ff-only` -> 开发/提交 -> `push`
- 副端（建议 SSH）：仅同步主端结果，不并发提交同一任务
- 副端若有本地改动：先 `stash`，同步后 `stash pop`

约束：

- 禁止两端分别先提交后再互拉。
- 若已出现双端分叉，回到主端统一整合。

## 5. 证据采集与记录要求

### 5.1 基线命令（必采）

```bash
git status -sb
git branch -vv
git log --oneline --decorate -n 20
git remote -v
```

### 5.2 决策记录最小字段

每次触发治理流程，至少记录以下字段到工作日志：

| 字段 | 说明 |
|------|------|
| 触发场景 | 例如 `push 被拒绝`、`rebase 中断` |
| 现场状态 | 分支状态、是否分叉、是否存在大体量目录变更 |
| 采取动作 | 具体命令链（merge / abort / rescue 分支） |
| 决策理由 | 为什么选该方案，为什么不选替代方案 |
| 结果状态 | 是否成功推送，是否与远端对齐 |

### 5.3 记录模板

```markdown
## Git 协作治理记录

- 触发场景：
- 现场状态：
- 采取动作：
- 决策理由：
- 结果状态：
- 关联分支与提交：
```

## 6. 禁止清单

以下行为默认禁止：

1. 在共享分支直接执行 rebase 并推送重写历史。
2. 未建立救援分支即进行高风险整合。
3. 以 `push --force` 替代标准冲突整合流程。
4. 忽略大体量数据目录对整合耗时和失败率的影响。
5. 双端并发提交后再尝试互拉自愈。

---

## 7. 例外审批

若必须偏离本规范（如历史清理、强推、非常规回滚），需满足：

1. 用户明确授权偏离动作和影响范围。
2. 已建立可回滚锚点（救援分支或标签）。
3. 在工作日志中记录偏离原因与恢复路径。

---

## 8. 验收清单

执行完成后，至少满足：

1. 本地分支与远端目标分支同步（无未预期分叉）。
2. 工作区状态可解释（干净或仅剩预期变更）。
3. 未使用未授权的破坏性操作。
4. 工作日志已记录“触发-决策-结果”闭环。

---

## 9. 最小提交约束

### 9.1 目标

本节定义计划型提交的最低可读性要求，确保按任务计划执行的提交从第一天起就有基本结构，而不是完全自由格式。

为什么：当 `development-governance` 的任务计划把"commit"列为 task 步骤时，如果提交信息完全没有约束，仓库历史会在项目初期就积累大量无结构提交，后续回溯成本很高。

### 9.2 适用范围

本约束仅适用于**按任务计划执行的提交**（即 task 中包含 commit 步骤的场景）。日常零散提交暂不强制。

### 9.3 最小要求

若 task 计划中包含 commit 步骤，则提交信息至少满足：

| 字段 | 要求 | 示例 |
|------|------|------|
| task 标识 | 标注所属 task 编号或名称 | `[task-3]`、`[新增退出门禁]` |
| 中文摘要 | 一句话说明本次提交做了什么 | `AGENTS.md §5 新增完成验证底线行` |

最小格式：

```
[task 标识] 中文摘要
```

示例：

```
[task-3] AGENTS.md §5 新增完成验证底线行
[新增退出门禁] development-governance SPEC.md 退出门禁追加完成验证引用
```

### 9.4 说明

- 本节**不是**完整的 `git-commit` 规范（如 Conventional Commits 的 type/scope 结构）。
- 完整提交规范将在 task 粒度完成至少一轮真实项目验证后再决定是否固化。
- 当前只要求最低限度的可读性保护。
