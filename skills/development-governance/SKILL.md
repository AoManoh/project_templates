# 开发治理 Skill

**skill_id**: `development-governance`
**版本**: 1.1.0
**output_dir**: `docs/development/`

---

## 1. 概述

本技能定义 AI Agent 执行非平凡开发任务时的治理流程，适用于新增能力、新接口、跨文件实现和需要明确验收标准的开发工作。

目标不是让代码“先能跑”，而是让单个开发 task 在当前轮次内完成事实确认、任务拆解、实现、验证、文档同步、清理和 review 闭环。

### 1.1 触发条件

| 触发方式 | 条件 |
|----------|------|
| 显式触发 | 用户指令包含关键词：`开发`、`实现`、`新功能`、`feature`、`需求落地`、`接口实现` |
| 场景触发 | 新增能力涉及多个文件、存在接口/配置/脚本同步要求，或需要明确完成定义与验证闭环 |

### 1.2 前置依赖

| 依赖 | 用途 | 必要性 |
|------|------|--------|
| auggie-mcp Skill | 源码语义检索、事实检索、影响面定位 | 必需 |
| view 工具 | 读取真实文件确认 | 必需 |
| code-review Skill | review 与验证证据采集 | 推荐 |
| docs/references/ | 记录外部依据与技术决策 | 推荐 |

## 2. 强制行为

| 行为 | 时机 |
|------|------|
| 读取 SPEC.md | 开始前 |
| 写入开发记录前，必须先确认项目根为当前 `AGENTS.md` 所在目录；所有 `docs/development/*` 路径相对该目录解析 | 开始实现前 |
| 先判断任务规模与适用边界 | 制定方案前 |
| 先确认唯一事实源和受影响文档 | 编辑前 |
| tasks 必须经过用户审核后再编码 | 开始实现前 |
| Skill 触发后必须生成开发闭环记录 | 开始实现前 |
| 每个 task 必须完成代码、测试、文档、验证、清理与 review 闭环 | task 退出前 |
| 临时方案必须写明退出条件并获得用户批准 | 采用临时方案前 |
| 完成一个 task 后必须先自检与 review，再推进下一 task | task 完成后 |

## 3. 快速参考

### 3.1 适用边界

| 任务规模 | 判定信号 | 处理要求 |
|----------|----------|----------|
| 小 | 单文件或局部修复、无新接口/新流程、无额外事实源同步 | 默认不自动触发本 Skill，按普通开发节奏执行 |
| 中 | 多文件改动、新增接口/配置/脚本、需要明确验收条件 | 触发本 Skill，并生成 `docs/development/` 记录 |
| 大 | 跨模块能力建设、存在阶段验收或高影响面 | 触发本 Skill；若核心问题是替换旧实现或迁移边界，改用 `refactor-governance` |

### 3.2 产物命名

```
docs/development/YYYY-MM-DD-{scope}.md
```

`scope` 使用 kebab-case，推荐采用功能名、接口名或模块名。

### 3.3 禁止事项速查

| 禁止事项 | 为什么 |
|----------|--------|
| 只完成 happy path | 会把边界条件与异常路径留给后续 task，形成验证债 |
| 代码已改但测试/文档未同步 | 会让“实现真相”和“说明真相”分裂 |
| 用 TODO 占位关键收尾动作 | TODO 不是闭环，只是未完成声明 |
| 新增第二份事实源但不废弃旧事实源 | 会导致后续 AI 和开发者引用不同基线 |
| 无退出条件地引入临时分支或特例逻辑 | 临时逻辑最容易永久化 |

## 4. Skill 定义

### 4.1 assess_scope_and_activate

**目的**: 判断任务是否值得引入开发治理成本，避免小题大做，也避免中大型任务裸奔。

**执行步骤**:
1. 判断改动是否涉及多个文件、接口、配置、脚本或外部文档同步。
2. 判断是否需要单独定义完成标准与验证清单。
3. 满足条件时，创建 `docs/development/YYYY-MM-DD-{scope}.md` 并进入后续步骤。

### 4.2 establish_single_source_of_truth

**目的**: 在编码前确认当前唯一权威事实源，避免开发过程中制造双重真相。

**执行步骤**:
1. 确认需求、架构、接口、配置的当前权威来源。
2. 列出会被此次开发影响的代码、文档、脚本和测试。
3. 在开发记录中写明“要同步哪些事实源”。

**关键约束**:
- 事实源不能只列代码文件，必须覆盖对应文档、脚本、配置和测试。

### 4.3 design_closed_loop_task

**目的**: 让 task 的完成定义在开始前就可审计，而不是做到一半再补解释。

**执行步骤**:
1. 写清目标、非目标、完成定义和验证方式。
2. 按 task 拆分实现顺序，并标出每个 task 的收尾动作。
3. 明确哪些风险需要在当前 task 内清掉，哪些需要用户显式批准后才能延后。

**计划编写细则**：task 拆分后的粒度标准、必填字段与验证命令要求详见 [SPEC.md §7](./SPEC.md#7-任务计划编写规范)。

### 4.4 execute_task_with_review

**目的**: 在实现阶段保持“做完一项、验证一项、review 一项”的节奏，避免半完成状态堆积。

**执行步骤**:
1. 按已审核的 task 逐项实现。
2. 每完成一个 task，立即执行对应测试、文档同步和代码 review。
3. 中高风险变更可并行委派子代理、人工 reviewer 或外部审查工具；主 AI 助手必须合并结论并处理阻塞问题。

### 4.5 close_task_without_residual_debt

**目的**: 确保 task 退出时不把隐性债务带入下一阶段。

**执行步骤**:
1. 对照完成定义检查代码、测试、文档、验证、清理是否齐全。
2. 清理无效注释、旧分支逻辑、过期脚本、错误文档和试验性代码。
3. 在开发记录中写明验证结果、剩余风险和用户批准的例外项。

**关键约束**:
- 未经用户批准，不得把“稍后补测试/补文档/补清理”作为默认退出方式。
