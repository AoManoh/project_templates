# 开发治理 Skill 规范

**版本**: 1.1.0
**适用范围**: 中风险及以上开发任务的进入门禁、退出门禁、计划标准与债务清理

---

## 1. 目标

本规范用于约束非平凡开发任务的进入门禁、退出门禁、记录模板与债务清理清单。

为什么：开发任务最常见的失败不是“不会写代码”，而是把半完成状态伪装成完成状态。

---

## 2. 进入门禁

开始编码前，必须同时满足以下条件：

1. 已读取 `AGENTS.md`、本 Skill 和本文件。
2. 已通过源码确认当前事实源与影响范围。
3. 已完成 tasks 拆分并得到用户审核确认。
4. 已明确验证方式：测试、构建、静态检查、手工验证或其组合。
5. 已在 `docs/development/YYYY-MM-DD-{scope}.md` 写明目标、非目标和完成定义。
6. 已按 AGENTS.md「Skill 调度与 owner 规则」判断主治理 Skill 与行为型 Overlay；若叠加 `pua`，其作用只限执行强度、失败恢复和证据压力，不改变本 Skill 产物目录。

---

## 3. 开发记录模板

开发记录至少包含以下章节：

1. **目标**：这次开发要交付什么。
2. **非目标**：这次明确不做什么，防止 scope 漂移。
3. **事实源**：需求、接口、配置、文档、测试分别以什么为准。
4. **任务拆分**：每个 task 的实现、验证和收尾动作。
5. **完成定义**：满足哪些条件才算真正完成。
6. **验证结果**：执行了什么验证，结果如何。
7. **清理记录**：删掉了哪些旧逻辑、过期注释、临时脚本或错误文档。
8. **例外项**：仅记录已获用户批准的临时方案及退出条件。

---

## 4. 退出门禁

task 退出前，必须满足以下条件：

| 类别 | 退出要求 |
|------|----------|
| 代码 | 功能实现与异常路径都已覆盖本次 scope |
| 测试 | 已执行与改动匹配的最小充分验证 |
| 文档 | 受影响的说明、注释、脚本、配置文档已同步 |
| Review | 已完成主 AI 助手自检；中高风险变更已补充人工、子代理或外部 reviewer 审查，并合并结论 |
| 清理 | 无无主 TODO、无失效分支、无未声明退出条件的临时逻辑 |
| 完成验证 | 满足 AGENTS.md 完成前证据门禁（`GATE-EVIDENCE`） |

---

## 5. 四类债务清单

### 5.1 技术债

- 无主的临时分支逻辑
- 只支持 happy path 的实现
- 未落地的错误处理或回滚逻辑

### 5.2 文档债

- 接口变了但 README / 注释 / ADR 未同步
- 输出目录、脚本入口、运行命令已变化但文档仍是旧值

### 5.3 验证债

- 改了代码但未运行对应测试或检查
- 只做“理论上应该能跑”的口头验证

### 5.4 半完成状态债

- task 已切换，但上一个 task 的清理仍未完成
- 例外项没有用户批准或没有退出条件

---

## 6. 规模匹配原则

| 场景 | 记录要求 |
|------|----------|
| 小任务 | 不强制启用本 Skill，避免制造额外文档负担 |
| 中任务 | 单份开发记录即可，重点写清完成定义与验证结果 |
| 大任务 | 允许多 task，但每个 task 仍需独立闭环，不得把收尾动作统统推迟到最后 |

---

## 7. 任务计划编写规范

### 7.1 目标

本节约束 task 拆分后的计划编写标准，确保每个 task 在执行前就具备可审计、可执行、可验证的完整描述。

为什么：如果 task 只有"实现 XXX 功能"这样的标题，执行者（AI 或开发者）会自由发挥填充细节，导致实现方向偏离、验证缺失或收尾遗漏。

### 7.2 粒度标准

每个 task 的预期执行时间应为 **2-5 分钟**。如果一个 task 预计超过 5 分钟，应拆分为更小的子 task。

判断标准：

| 信号 | 处理 |
|------|------|
| task 描述需要超过 3 句话解释"怎么做" | 考虑拆分 |
| task 涉及多个文件且修改逻辑不同 | 应拆分 |
| task 包含"先做 A，再做 B，最后做 C" | 拆为 3 个 task |
| task 只需修改一处且验证方式明确 | 粒度合适 |

### 7.3 必填字段

每个 task 至少包含以下信息：

| 字段 | 说明 | 示例 |
|------|------|------|
| 目标 | 这个 task 做什么 | "为 `parseConfig` 增加缺失字段的默认值处理" |
| 文件路径 | 需要修改的文件 | `src/config/parse.ts` |
| 修改内容 | 具体要改什么（含代码片段） | "`timeout` 缺失时回退默认 30s，并补充类型校验" |
| 验证命令 | 如何验证修改正确 | `npm test -- config.parse` |
| 期望输出 | 验证命令的预期结果 | "缺失字段用例通过，无回归" |

### 7.4 计划文档头模板

当计划包含 3 个以上 task 时，建议在计划开头写明：

```markdown
## 计划概述

- **目标**：本轮计划要达成什么
- **范围**：涉及哪些文件/模块
- **前置条件**：开始前需要确认什么
- **task 数量**：N 个
- **预计总时间**：X 分钟
```

### 7.5 禁止事项

| 禁止事项 | 为什么 |
|----------|--------|
| task 只有标题没有修改内容 | 执行者会自由发挥，偏离预期 |
| task 没有验证命令 | 无法判断 task 是否真正完成 |
| 多个 task 共享同一个验证步骤 | 前面的 task 完成状态无法独立确认 |
| 把"验证所有改动"作为最后一个 task | 验证应该内嵌到每个 task，不应后置 |
| 出现 `TBD`、`TODO`、`后续补充`、`适当处理` 等占位语 | 占位语会把关键设计、错误处理或验证责任留到执行时自由发挥 |
| 只写"添加错误处理 / 补测试 / 更新文档"但不写具体路径和验收方式 | 这不是计划，是愿望；执行者无法独立判断完成状态 |

### 7.6 计划自审

计划提交用户审核前，必须自审：

| 检查项 | 要求 |
|--------|------|
| 需求覆盖 | 每个已确认需求、非目标和完成定义都能对应到具体 task 或明确不做说明 |
| 事实源覆盖 | 涉及代码、配置、脚本、测试、文档时，计划写明要同步哪些当前事实源 |
| 验证独立 | 每个 task 都有自己的验证命令或检查方式，不能依赖最后统一验证兜底 |
| 名称一致 | 后续 task 引用的函数、类型、路径、配置名必须与前置 task 保持一致 |
| 占位清零 | 不存在 `TBD`、`TODO`、`后续补充`、`类似上一步` 等占位表达 |

### 7.7 与提交约束的联动

当 task 计划中包含 commit 步骤时，提交信息必须满足 [git-governance SPEC.md §9 标准提交信息规范](../git-governance/SPEC.md#9-标准提交信息规范)的要求。提交必须包含 body，并写清背景、变更、影响与边界。
