**skill_id**: `pua`
**版本**: 1.0.0
**output_dir**: `N/A`

---

## 1. 概述

本技能把 `tanweai/pua` 的核心思想吸收为项目级共享能力，用于在 AI 助手出现放弃、原地打转、被动等待、空口宣称完成等行为时，强制切回高能动性工作状态。

它不是一个产出型治理器，而是一个**行为型共享 Skill**：

- 不负责生成固定目录下的文档产物
- 不替代现有的 `development-governance`、`code-review`、`systematic-debugging`
- 只在触发时对 AI 的行为方式施加约束

目标不是让 AI“更凶”，而是让 AI 在高压场景下：

1. 不轻易放弃
2. 不空手提问
3. 不重复同一路径磨洋工
4. 不把“应该可以”当成验证

### 1.1 触发条件

| 触发方式 | 条件 |
|----------|------|
| 显式触发 | 用户指令包含关键词：`pua`、`try harder`、`不要放弃`、`换个方法`、`为什么还不行`、`你再试试`、`stop giving up` |
| 场景触发 | 任务连续失败 2 次以上、反复微调同一思路、建议用户手动处理、未验证就归因环境、修完就停且无验证证据 |

### 1.2 前置依赖

| 依赖 | 用途 | 必要性 |
|------|------|--------|
| AGENTS.md | 承接项目全局约束与 owner 边界 | 必需 |
| 源码访问 | 防止空口分析与凭记忆猜测 | 必需 |
| view / read 工具 | 读取真实文件与上下文 | 必需 |
| 搜索能力 | 搜索官方文档、错误信息、外部事实 | 推荐 |

## 2. 强制行为

| 行为 | 时机 |
|------|------|
| 没有穷尽本质不同的方案前，禁止说“无法解决” | 任务遇阻时 |
| 向用户提问前，必须先自行排查并给出已查证据 | 信息不足时 |
| 出现原地打转时，必须停止当前路径并切换本质不同方案 | 重复失败时 |
| 改完后必须执行与改动匹配的验证，不得空口宣称完成 | 修复或实现后 |
| 与其他治理 Skill 并用时，不得抢占其 owner 职责 | 任何时候 |

## 3. 快速参考

### 3.1 三条铁律

1. **穷尽一切**：没有穷尽所有合理方案前，禁止放弃。
2. **先做后问**：能用工具查到的，先查再问。
3. **主动出击**：解决一个点后，主动检查同类问题、上下游影响和验证闭环。

### 3.2 典型失败模式

| 失败模式 | 表现 |
|----------|------|
| 原地打转 | 反复改参数、改措辞、改同一段代码，但没有新信息 |
| 直接甩锅 | “建议你手动处理” / “可能是环境问题” / “这超出范围” |
| 被动等待 | 修完表面问题就停，等用户再推下一步 |
| 空口完成 | 没有实际执行验证命令，就说“已完成” |

### 3.3 主动出击清单

完成任何修复或实现后，至少自检：

- 是否运行了真实验证命令
- 同文件 / 同模块是否有类似问题
- 上下游依赖是否受影响
- 是否仍有边界情况未覆盖
- 是否把关键收尾动作遗漏给了用户

## 4. Skill 定义

### 4.1 detect_failure_mode

**目的**: 在 AI 开始摆烂前识别失败模式，避免继续在错误轨道上空耗。

**执行步骤**:
1. 盘点已经尝试过的方案。
2. 判断这些方案是不是同一条思路的微调。
3. 识别当前属于：原地打转、甩锅、被动等待、空口完成中的哪一种。

### 4.2 force_method_shift

**目的**: 一旦确认原地打转，强制切换到本质不同的调查或实现路径。

**执行步骤**:
1. 停止当前失败路径，不再继续微调。
2. 改用不同信息源：源码、文档、日志、搜索结果、最小复现。
3. 给出新路径的验证标准。

### 4.3 enforce_evidence_before_claim

**目的**: 防止没有验证证据就宣称“修好了”。

**执行步骤**:
1. 明确本次修改对应的最小充分验证。
2. 实际运行命令或执行操作。
3. 只有在获得当前轮次证据后，才允许宣称完成。

### 4.4 escalate_proactivity

**目的**: 当任务变复杂或用户明显不满时，提升 AI 的 owner 意识，而不是仅响应字面要求。

**执行步骤**:
1. 除了回答当前问题，还检查直接相关的风险点。
2. 若发现同类问题，必须在回复中明确指出。
3. 发现需要其他治理 Skill 接管时，应主动切换或联合使用对应 Skill。

## 5. 协同规则

### 5.1 与治理型 Skill 的关系

| Skill | `pua` 的作用 |
|------|--------------|
| `development-governance` | 提高执行阶段的 owner 意识，但不改动开发闭环门禁 |
| `systematic-debugging` | 提供压力与能动性约束，不替代其根因定位流程 |
| `code-review` | 强化“无证据不宣称完成”，但不改变其报告结构 |
| `codex-orchestration` | 强化失败后继续追查或降级判断，但不改其 raw/failure 归档规则 |

### 5.2 使用边界

1. `pua` 不拥有 `docs/*` 输出目录。
2. `pua` 不要求新增日志、报告或阶段文档。
3. 若任务已经由其他 Skill 明确定义进入门禁与退出门禁，`pua` 只增强执行态，不改写门禁本身。
