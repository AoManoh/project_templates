# 需求治理 Skill

**skill_id**: `requirements-governance`
**版本**: 1.0.0
**output_dir**: `docs/requirements/`

---

## 1. 概述

本技能定义 AI Agent 在需求对齐阶段的治理流程，确保需求从模糊意图转化为可审计的结构化产物，而不是 AI 自由发挥的开放式对话。

目标不是替代用户决策，而是让需求澄清有节奏、方案对比有结构、边界确认有闭环。

### 1.1 触发条件

| 触发方式 | 条件 |
|----------|------|
| 显式触发 | 用户指令包含关键词：`需求`、`讨论需求`、`需求对齐`、`brainstorming`、`方案讨论`、`PRD` |
| 场景触发 | 项目初始化阶段的需求讨论、功能方案对比、技术选型讨论、需求边界不清晰时 |

### 1.2 前置依赖

| 依赖 | 用途 | 必要性 |
|------|------|--------|
| AGENTS.md | 项目定位与技术栈约束 | 必需 |
| view 工具 | 读取现有需求文档与代码 | 必需 |
| docs/references/ | 外部调研与技术决策参考 | 推荐 |

### 1.3 关联规范

详细约束见：[SPEC.md](./SPEC.md)

## 2. 强制行为

| 行为 | 时机 |
|------|------|
| 读取 SPEC.md | 开始前 |
| 写入需求产物前，必须先确认项目根为当前 `AGENTS.md` 所在目录；所有 `docs/requirements/*` 路径相对该目录解析 | 讨论收敛后 |
| 先澄清再方案，先方案再细节 | 需求讨论时 |
| 每轮对话必须收敛至少一个边界 | 讨论过程中 |
| 方案对比必须有结构化呈现 | 提出方案时 |
| 需求产物必须写入 output_dir | 讨论收敛后 |
| 不得在用户未确认时擅自进入开发阶段 | 阶段切换前 |

## 3. 快速参考

### 3.1 适用边界

| 需求规模 | 判定信号 | 处理要求 |
|----------|----------|----------|
| 小 | 单一功能点、边界清晰、无技术选型争议 | 不强制触发本 Skill，正常沟通即可 |
| 中 | 涉及多个模块交互、存在方案取舍、需要明确完成定义 | 触发本 Skill，生成需求记录 |
| 大 | 跨模块能力建设、涉及架构选型、需要多轮迭代确认 | 触发本 Skill，生成完整需求文档（含 PRD） |

### 3.2 产物命名

```
docs/requirements/YYYY-MM-DD-{scope}.md
```

`scope` 使用 kebab-case，推荐采用功能名或需求主题。

### 3.3 禁止事项速查

| 禁止事项 | 为什么 |
|----------|--------|
| 需求未澄清就跳入实现细节 | 会在错误的方向上投入大量精力 |
| 只给一个方案不给对比 | 用户无法判断该方案的取舍代价 |
| 用技术术语替代需求描述 | 需求应该是用户可审计的，不是只有开发者能看懂的 |
| 讨论发散后不收敛 | 需求对齐的目标是收敛，不是头脑风暴 |
| 未经用户确认就进入开发 | 需求边界是用户的决策权，不是 AI 的 |

## 4. Skill 定义

### 4.1 clarify_intent

**目的**: 把用户的模糊意图转化为可审计的需求陈述，避免 AI 基于假设自由发挥。

**执行步骤**:
1. 提炼用户意图的核心目标。
2. 列出需要用户确认的关键假设。
3. 明确本次需求的边界：做什么、不做什么。

### 4.2 compare_solutions

**目的**: 让方案选择有结构化的对比依据，而不是 AI 单方面推荐。

**执行步骤**:
1. 列出候选方案（至少两个）。
2. 用统一维度对比：实现成本、维护成本、扩展性、风险。
3. 标注 AI 的推荐及理由，但最终选择权交给用户。

### 4.3 define_acceptance_criteria

**目的**: 在进入开发前就明确"做到什么程度才算完成"，避免做完后才发现预期不一致。

**执行步骤**:
1. 将已确认的需求转化为可验证的完成定义。
2. 区分必要条件和锦上添花条件。
3. 标注验证方式：自动测试、手动验证、用户确认。

### 4.4 produce_requirements_document

**目的**: 将讨论收敛后的需求固化为可追溯的文档产物。

**执行步骤**:
1. 按 SPEC.md 模板生成需求文档。
2. 写入 `docs/requirements/YYYY-MM-DD-{scope}.md`。
3. 在文档中标注未决项和需要后续确认的内容。

## 5. Skill 编排流程

### 5.1 标准需求对齐流程

```
1. clarify_intent
   |
2. compare_solutions（按需）
   |
3. define_acceptance_criteria
   |
4. produce_requirements_document
   |
5. 用户确认 → 进入开发阶段
```

### 5.2 快速需求确认流程（小规模）

```
1. clarify_intent（简化）
   |
2. 用户确认 → 进入开发
```
