# 需求治理 Skill 规范

**版本**: 1.1.0
**适用范围**: 新项目启动、需求对齐、方案讨论、PRD 生成

---

## 1. 目标

本规范用于约束需求对齐阶段的讨论节奏、产物结构和阶段退出标准。

为什么：需求阶段是最怕 AI 自由发挥的阶段。如果没有结构化的讨论节奏，AI 容易基于假设直接给出方案，跳过用户真正需要确认的边界问题。

---

## 2. 讨论节奏约束

需求讨论必须分阶段推进，禁止跳跃：

| 阶段 | 目标 | 退出条件 |
|------|------|----------|
| 意图澄清 | 用户想解决什么问题 | 用户确认核心目标和边界 |
| 决策树追问 | 哪些不确定性会改变方案方向 | 阻塞性决策已逐项确认或转为未决项 |
| 方案对比 | 有哪些可选方案，各有什么代价 | 用户选定方案方向 |
| 细节确认 | 选定方案的具体实现要求 | 完成定义和验证方式已明确 |
| 产物输出 | 将讨论结果固化为文档 | 需求文档已写入 output_dir |

### 2.1 决策树追问规则

需求不清晰时，不允许一次性抛出长问题清单。必须先把不确定性整理成决策树，按“是否会改变范围、架构、验收或风险等级”排序。

硬要求：

1. 能通过代码库、AGENTS、当前阶段文档、配置或测试确认的问题，必须先自查，不得转嫁给用户。
2. 每轮最多问一个阻塞性问题；问题必须能收敛一个明确边界。
3. 每个问题必须附带 AI 推荐答案、推荐理由和选择影响，方便用户直接批准或修正。
4. 用户回答后，必须更新已确认边界、候选方案和未决项，再进入下一问题。
5. 如果问题不阻塞当前阶段，必须记录为未决项，不得打断主线。

---

## 3. 需求文档模板

`docs/requirements/YYYY-MM-DD-{scope}.md` 至少包含：

1. **需求背景**：为什么需要这个功能或变更。
2. **核心目标**：这次要解决的具体问题。
3. **非目标**：明确不在本次范围内的内容。
4. **关键决策**：已确认的关键选择、推荐理由和取舍影响。
5. **方案概述**：选定方案的简要描述。
6. **方案对比**（中大型需求）：候选方案的结构化对比。
7. **完成定义**：满足哪些条件才算完成。
8. **验证方式**：如何验证完成定义。
9. **未决项**：仍需后续确认的内容。

---

## 4. 新项目启动产物模板

新项目启动固定产物路径：

```text
docs/requirements/YYYY-MM-DD-project-kickoff.md
```

文档至少包含：

1. **项目背景**：为什么要启动这个项目，面向谁解决什么问题。
2. **核心定位**：一句话说明项目是什么，不是什么。
3. **目标用户与使用场景**：主要用户、核心工作流、典型输入输出。
4. **核心目标**：本项目第一阶段必须达成的结果。
5. **非目标**：明确不在第一阶段处理的能力、平台、集成或优化。
6. **关键决策**：技术栈、架构方向、数据模型、部署/运行方式、权限与隐私边界等已确认选择。
7. **方案对比**：存在技术选型或架构取舍时，列出候选方案、推荐方案、理由与代价。
8. **AGENTS.md 实例化清单**：列出需要写入 AGENTS.md 的项目名称、核心定位、技术重心、架构图、目录结构、依赖表、验证命令表和环境片段选择。
9. **完成定义与验证方式**：项目初始化完成的判定条件，包括 AGENTS.md 已补齐、用户已审核、验证入口已明确。
10. **参考资料**：引用 `docs/references/` 中对当前决策有效的调研文档；未被引用的参考资料只作背景。
11. **未决项与后续阶段**：可以延后但不得阻塞 AGENTS 审核的事项，以及进入开发阶段后的首批候选 task。

项目启动需求文档是 AGENTS.md 实例化前的阶段事实源；AGENTS.md 经用户审核后成为项目级约束的唯一权威来源。若二者后续发生冲突，必须暂停并由用户确认当前权威来源，不得让 AI 在两份事实中自行取舍。

## 5. PRD 产物模板（大型需求）

当需求规模较大时，可生成结构化 PRD：

```markdown
# {功能名称} 产品需求文档

## 1. 背景与目标

### 1.1 背景
为什么需要这个功能。

### 1.2 核心目标
解决什么问题，达到什么效果。

### 1.3 非目标
明确不做什么。

## 2. 方案设计

### 2.1 方案概述
选定方案的整体描述。

### 2.2 方案对比

| 维度 | 方案 A | 方案 B | 选定方案 |
|------|--------|--------|----------|
| 实现成本 | ... | ... | ... |
| 维护成本 | ... | ... | ... |
| 扩展性 | ... | ... | ... |
| 风险 | ... | ... | ... |

### 2.3 选择理由
为什么选这个方案。

## 3. 详细需求

### 3.1 功能需求
具体功能点。

### 3.2 非功能需求
性能、安全、兼容性等。

## 4. 完成定义与验证

| 完成条件 | 验证方式 | 必要性 |
|----------|----------|--------|
| 条件 1 | 测试/手动验证 | 必要 |
| 条件 2 | 用户确认 | 必要 |

## 5. 未决项与风险

- 未决项 1
- 风险 1
```

## 6. 退出门禁

需求阶段退出前，必须满足以下条件：

| 类别 | 退出要求 |
|------|----------|
| 目标 | 核心目标和非目标已明确且用户已确认 |
| 方案 | 选定方案有明确理由，非默认接受 AI 推荐 |
| 边界 | 做什么和不做什么已明确 |
| 决策 | 阻塞性决策已逐项确认，或作为未决项显式记录 |
| 完成定义 | 满足条件和验证方式已写入需求文档 |
| 产物 | 需求文档已写入 `docs/requirements/` |
| 完成验证 | 满足 AGENTS.md §5 完成验证底线 |

新项目启动额外门禁：

| 类别 | 退出要求 |
|------|----------|
| 项目事实 | 项目名称、定位、目标、非目标、技术栈、目录结构、核心模块和验证入口已明确 |
| AGENTS 输入 | `AGENTS.md` 所需占位符已有明确内容，或未决项已标注为不阻塞审核 |
| 外部依据 | 技术选型或架构对比所依赖的资料已归档到 `docs/references/` 并被需求文档引用 |
| 阶段切换 | `AGENTS.md` 与项目启动需求文档已经交给用户审核；未经确认不得进入开发治理或编码 |

---

## 7. 禁止清单

1. 在用户未确认核心目标前，直接给出实现方案。
2. 只提供一个方案且不说明替代选项。
3. 把需求讨论的结论留在聊天记录中，不写入产物文档。
4. 在需求边界未收敛时进入开发阶段。
5. 用 AI 假设替代用户决策。
6. 能读取事实源却把问题抛给用户。
7. 一次性提出多个互相独立的问题，导致用户无法逐项裁决。
8. 新项目启动时跳过 `docs/requirements/YYYY-MM-DD-project-kickoff.md`，直接填写 AGENTS.md 或直接编码。
9. 把未被当前需求文档或 AGENTS.md 引用的外部参考资料当成当前决策事实。
