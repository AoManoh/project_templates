# 需求治理 Skill 规范

**版本**: 2.0.0
**适用范围**: requirements-governance 需求产物、事实源交接和退出证据

---

## 1. 目标与边界

本规范只定义需求产物应表达的语义、事实源权威切换、project-kickoff/PRD 细则和 handoff 证据，不重复 SKILL 中的 owner 判定、提问流程、blocker 行为或方案比较规则。

## 2. 事实源与权威切换

| 领域 | 当前权威来源 |
|---|---|
| 用户最新明确的业务决定 | 用户当前对话中的最新确认；handoff 前必须同步到当前需求产物 |
| 当前 scope 的业务 Goal、非目标、业务决策和业务验收 | 已同步用户最新确认的当前需求产物 |
| 项目级环境、工具、目录、依赖、公开性和治理约束 | 联合审核后的 AGENTS |
| 当前代码实际行为 | 源码、配置、测试和运行结果 |
| 实现 task、文件、测试命令和技术闭环 | development/refactor 产物 |
| 外部事实 | 实际可访问的一手/权威来源；`docs/references/` 只在已执行并含真实信源时作为证据载体 |

不同领域的事实源不互相覆盖。用户最新确认即时优先；requirements 必须在 handoff 前将其同步到当前需求产物，不得用旧文档覆盖用户最新决定。

同一 scope 默认更新同一当前需求产物。确需创建替代文件时：

1. 新文件在用户确认前只是草稿，旧已确认文件继续保持当前权威。
2. 用户确认新文件后才切换当前权威。
3. 当前新文件声明被替代的旧路径，不强制回写所有历史文件。
4. handoff 时同一 scope 恰好只有一个经用户确认的当前需求事实源。
5. 外部证据和 implementation 计划不得冒充需求事实源。

## 3. 通用需求产物

普通需求产物路径：

```text
docs/requirements/YYYY-MM-DD-{scope}.md
```

`scope` 使用 kebab-case，并按仓库已有命名确定当前 scope 的唯一产物。

需求产物应表达以下语义，但不要求固定标题、空栏目或每项都存在：

1. **背景与 Goal**：为什么做、面向谁、用户可观察的预期业务结果。
2. **非目标**：当前 scope 明确不解决什么。
3. **确认业务决策及真实依据**：依据可以是用户直接确认、适用规则、仓库事实或外部证据；只有确实由 AI 推荐时才记录推荐理由和代价。
4. **业务验收**：用户可观察、可判定的成功结果，不写 implementation task 或测试命令。
5. **条件性前提**（存在时）：适用边界、前提失效的影响和重新进入条件。
6. **未决项**（存在时）：草稿可记录 blocker 及缺少的裁决或证据；只有非阻塞未决项可以随 handoff 留存，并说明它为什么不阻塞及下游需要知道的影响。
7. **Handoff 信息**：下一 owner、有效条件性前提、非阻塞未决项和业务边界。

需求产物头部只保留最小审核状态：

```text
待用户确认
已确认
```

提交用户审核时应说明：用户批准当前产物即同时授权将状态改为 `已确认`；只修改该状态不需要再次审核。任何语义内容变化都必须先恢复为 `待用户确认` 并重新审核。

未获用户确认的判断不得写入“确认业务决策”。用户明确陈述本身可以构成对应事项的确认，不要求固定确认话术。

最终产物的确认依据是实际用户消息或等价外部审批，不由 AI 预先声明。精确产物路径由 handoff 消息提供，需求文档不写自引用路径或确认日期。

## 4. 产物中的证据与取舍

本节只定义产物如何表示 SKILL 已取得的证据和裁决结果。

1. 关键决定实际依赖外部事实时，记录事实结论、实际可访问来源及它支持的决定；时效性事实再记录适用版本或日期及获取日期。
2. 单事实可以直接记录；多步调研有独立 reference 时只引用其已执行结论和路径，纯搜索计划不构成证据。
3. 优先一手或权威来源，但必须如实记录实际使用的来源，不虚构官方信源。
4. 外部来源和 references 提供证据，当前需求产物负责说明证据如何影响已确认业务决定。
5. 有真实替代时记录会影响用户选择的比较结果；没有真实替代时不制造 A/B 表格，高影响唯一方向记录排除依据。

## 5. Project-kickoff

新项目固定产物为：

```text
docs/requirements/YYYY-MM-DD-project-kickoff.md
```

它作为 AGENTS 实例化前的阶段事实源，应包含：

- 项目背景、核心定位、目标用户和主要场景；
- 第一阶段 Goal、非目标和用户可观察结果；
- 技术栈、架构方向、目录、核心模块和关键依赖；
- 运行/部署、安全、隐私和仓库公开性形态；
- 验证入口；
- 被当前决定实际使用的外部证据；
- blocker、非阻塞未决项和 handoff 边界。

requirements 根据 kickoff 实际实例化 AGENTS，并按 AGENTS 的公开性规则处理仓库形态和 `.gitignore`，不在本规范复制公开性机制。

project-kickoff 与 AGENTS 必须一起交给用户审核；确认前不得进入开发。kickoff 不列 implementation task，也不另建 AGENTS 实例化 checklist。

联合审核后：

1. AGENTS 唯一裁决当前项目级环境、工具、目录、依赖、公开性和运行约束。
2. project-kickoff 继续裁决本阶段业务 Goal、非目标和业务验收，并保留项目级值在批准时的审计快照。
3. 不要求两个文件持续双向同步；只有 AGENTS 变化同时改变业务契约时，才更新并重新确认需求产物。

## 6. 大型需求与 PRD

PRD 是当前需求产物的一种按需组织方式，不因“PRD”名称额外维护第二事实源。

在第 3 节语义基础上，只有确有需要时才展开用户流程、详细业务需求、非功能业务约束和复杂业务验收。方案对比仍为条件内容，不固定 `方案 A / 方案 B` 表格。

## 7. 退出与 handoff 证据

requirements handoff 时必须可观察到：

- 当前需求产物完整表达适用于本 scope 的 Goal、非目标、确认业务决策和可判定业务验收；
- 草稿中的业务 blocker 已关闭，仅非阻塞未决项随 handoff 留存；
- 关键决定实际依赖的仓库事实或外部证据可追溯；
- 同一 scope 不存在竞争性的当前需求事实源；
- 产物本身不会迫使 implementation owner 猜测未记录的业务行为；“无 blocker”或“已批准”文字不能替代这项检查；
- 存在覆盖最终产物的真实用户确认消息或等价审批，且产物审核状态已经按授权更新为 `已确认`；
- handoff 消息给出精确产物路径、下一 owner、有效条件性前提和非阻塞未决项；
- 新项目额外完成 project-kickoff 与 AGENTS 联合审核。

`GATE-EVIDENCE` 在需求阶段只证明上述产物、证据、用户确认和 handoff 真实存在，不表示代码实现或运行效果已经完成。

## 8. 读取方式

1. 先由 SKILL 完成 owner 复核；不拥有则 handoff，不读取本文件。
2. requirements 取得 owner 并选定当前需求事实源后，读取本文件。
3. 当前工具只能整文件读取时，如实加载完整 SPEC，不声称按章节读取。
4. 只有 eval 显示 PRD 或 kickoff 低频细节造成明显上下文负担时，才提出拆分 reference。
5. 评测语料、hidden cases、grader 和客户端实验不进入运行时 SKILL/SPEC。
