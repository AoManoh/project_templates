# 工程写作风格 Skill 规范

**版本**: 1.3.1  
**适用范围**: 工程项目中的所有可见文字，包括临时回复、进度说明、TODO、任务标题、工作日志、技术解释、owner 已决定的标识符命名、必要注释、文档、审查文字、提交说明和最终工作汇报

## 1. 优先级与默认读者

### 1.1 规则优先级

1. 系统、平台安全边界和项目 `AGENTS.md` 的不可破门禁；
2. 用户在门禁范围内对业务目标、取舍、动作授权和交付语气的当前明确决定；
3. 当前 primary owner 对流程和产物格式的专用规范；
4. 语言格式化配置、静态检查配置和稳定代码约定；
5. 本规范的通用表达规则。

用户决定业务目标和表达偏好，但不能把未经证实的实现或运行判断变成事实。本规范不以“写得更通俗”为理由改写精确协议字段、代码标识符、错误原文或机器格式。

### 1.2 默认读者与受众政策表

默认读者是能理解项目目标、但不了解当前实现细节的普通项目同事。产品、开发、测试、运营或新加入的同事应能看懂主体内容。

专业细节放在解释之后。不能通过删除必要条件、错误路径或技术名词来换取表面简单。

产物的 owner 规范已定义读者时，按下表切换读者档；不得把两档要求叠加到同一段文字上。本表是全部写作类规范共同引用的唯一受众事实源。

| 产物 | 读者档 | 术语政策 |
|---|---|---|
| 提交信息、PR 描述 | 工程师（git-governance SPEC §9.1 定义） | 通用工程术语直接使用；项目私有概念首次出现给一句作用说明；标题与背景段写行为变化，机制名称放变更段 |
| 代码注释 | 维护该代码的工程师与读源码的 AI | 同工程师档；只写理由和不能改动的约束（见 §5） |
| 临时回复、进度说明、最终汇报 | 普通项目同事 | 开头先用零术语业务语言给出结果；正文技术细节按 §3 解释项目私有概念 |
| 需求、设计、说明文档 | 普通项目同事与未来接手的 AI | 标准术语首次出现解释；项目私有概念解释并给可核对指针 |
| 工作日志、治理产物 | 未来接手的工程师与 AI | 工程师档；内部代号必须附产物路径指针 |
| 面向使用者的版本说明 | 不读代码的使用者 | 只写可观察行为变化和迁移动作，不出现内部机制名称 |

通用工程术语指有权威定义、目标读者档普遍掌握的词，例如 HTTP、JSON、JSONL、API、CLI、IDE、goroutine、RSS、p50、mmap、MiB。对工程师读者档，禁止给这类词加括号定义；对普通同事读者档按 §3.1 处理。项目私有概念指仅本项目使用的机制、文件或配置身份（如某个暂存日志、索引子树、配置指纹），任何读者档都必须在首次出现时给一句作用说明。

### 1.3 自包含检查

移除链接、文件路径和引用后，正文仍应回答适用的问题：

- 当前讨论什么问题；
- 项目现在怎样处理；
- 谁执行什么动作；
- 数据或状态怎样变化；
- 使用者看到什么结果；
- 结论由什么证据支持；
- 哪些范围尚未验证。

引用可以证明这些内容，但不能替正文回答。

## 2. 直白表达

### 2.1 过程说明

描述过程或动作时，优先写成：

```text
执行者 + 动作 + 对象 + 结果
```

定义、状态、数据格式和约束不必强行补执行者，应写清含义、成立条件和影响。例如，与其写“完成了配置优化”，不如写“API 客户端读取超时配置，并把该值应用到每次请求”。这里的例子只演示表达方式，不代表任何具体项目事实。

### 2.2 主动语态与例外

默认使用主动语态，明确是用户、浏览器、服务、任务还是脚本在执行动作。以下情况可以使用被动语态：

- 执行者未知且无法查明；
- 执行者与当前决定无关；
- 结果对象是本段主题，主动句反而更绕。

即使不用“被”字，也要检查“完成处理、进行优化、实现保障、问题得到解决”等抽象句是否隐藏了实际动作。

### 2.3 隐喻化工作简称硬门禁

隐喻化工作简称是把具体条件、组件动作或结果压缩成形象词、自造标签、拟人化简称或会话内代号的表达。所有可见输出一律禁止使用，不由模型判断“是否足够形象”或“项目里是否已经常用”。旧提交、旧文档、用户引用之外的来源文本和模型先前输出都不能授权继续沿用。

仅允许两类可核验例外：

1. 与源码、协议、API、配置或产品界面逐字一致的精确标识符，必须使用代码格式写出原名，不能只写新造的中文简称；
2. 有权威规范或项目术语表定义的标准技术术语，第一次出现时解释含义和当前影响。

不属于以上两类时，必须改写为：

```text
具体主体 + 触发条件 + 实际动作 + 可观察结果
```

来源只给出简称、没有给出对应事实时，必须回到代码、测试、配置或当时记录取证。无法取证时标明缺失信息并停止相关结论，不能把原简称换成“四类场景”“保护层”“控制面”等另一个抽象说法继续写。

禁止示例包括但不限于：索引风暴、车道、逃生门、速率地板、保险丝、闸、换血、续命、续跑、降速续跑、拉满、钉住、红转绿、淹没、机械臂、向量臂、赋能、抓手和底座。动词式简称（续跑、续命、换血、钉住）与名词式简称同等禁止，不因“读起来像普通动词”而豁免。审查或引用这些错误表达时，可以用引号指出原词，但必须在同一句或下一句给出直白替换。

### 2.4 直白替换

| 不使用 | 改写方向 |
|---|---|
| 索引风暴 | 索引请求连续收到 429 |
| 查询车道与索引车道分离 | 查询请求和索引请求使用独立控制路径 |
| 逃生门 | 将指定配置设为 `off` 时恢复旧行为 |
| 速率地板 | 允许降低到的最低请求速率 |
| daemon 换血 | daemon 在会话期间被替换 |
| 会话续命 | 升级后会话无需重启 |
| 降速续跑 | 降低请求速率继续处理 |
| 测试钉住 | 回归测试固定该行为 |
| 红转绿 | 修复前测试失败，修复后测试通过 |
| 被候选淹没 | 被其他候选挤出结果集 |
| 四象限 | 四类测试场景，并列出具体场景 |

同一硬门禁适用于企业套话和空洞评价。“赋能、抓手、底座、闭环、全链路、端到端、拉通、协同、对齐、体系、机制、矩阵、优化、提升、增强、智能、稳定、可靠”等词，除 §2.3 两类可核验例外外一律不用，直接改写为具体对象、前后差异和可观察结果。

### 2.5 能力判断词

“无法、不能、不可能、永远、根本”是能力断言，宣称某事在任何实现下都不成立。实现缺陷和功能缺失不满足这个标准：上限没有参与清理是“未生效”，接口没有提供是“没有提供”。把可修复缺陷写成“无法”，会让认真读者把实现缺陷复原成原理限制，得出错误机制。

1. 描述缺陷、缺失或旧行为时，写代码实际做了什么、没做什么：“字节上限没有参与清理”“daemon 没有提供列出状态的接口”“这些 key 在日志中没有对应记录”。
2. 能力判断词只在原理性限制确实成立时保留，且同句给出依据：语言或协议机制（如 Go 类型断言不展开错误链，需改用 `errors.As`）、可核验的恒等或数量关系（如桶容量恒等于一分钟目标而该批估算超过目标）、权威文档声明的边界。
3. 分不清是缺陷还是原理限制时，先回到代码、文档或运行记录取证；取证不了就只写观察到的行为，不写能力断言。
4. 本节约束缺陷与行为描述；逐字转录错误原文或引用他人措辞时保留原文，按 §4 标注来源。

扫描清单（供输出前检查与回归使用）：无法、不能、不可能、永远、根本。命中即核对第 2 条要求的依据是否在同句给出。

### 2.6 真实正反例

反例取自真实提交历史与未采用的重写草稿（原文样本存于 `fixtures/`），正例为按本规范改写后的形态。

**隐喻化简称（违反 §2.3）**

> 反例：吞吐治理器与车道分离——429 降速续跑，查询不受索引风暴拖累
> 正例：将查询与索引请求分开限流和熔断：索引请求连续收到 429 时降低速率继续执行，查询请求不再被索引侧故障阻塞

为什么错：风暴、车道、续跑是会话内比喻，读者复原不出触发条件和实际动作；正例写出主体、条件、动作、结果，并保留 429 原名。

**考古式叙述（叙述者错位）**

> 反例：未找到当期独立执行记录；仅核对了新增测试断言。测试代码存在不代表这些断言当期已经执行。
> 正例：`governor_test.go` 新增两项断言通过：65536-token 批在桶装满后放行；后续 1000-token 请求等待偿还超额。

为什么错：持久化产物的叙述者是当事工程师；“未找到记录”是事后整理者的取证处境，属工作日志内容。没有记录时省略该结论，不写取证过程。

**通用术语词典化与免责模板（违反 §1.2 读者档）**

> 反例：查询耗时 p50（第 50 百分位，即排序后中间位置的样本）为 75 ms。该数字只适用于所测工作区和硬件。
> 正例：实测查询耗时 p50 为 75 ms。

为什么错：工程师读者档给通用术语加定义是噪声；实测数字默认按实测陈述，只有数字被用来支撑普适结论时才写一次适用范围。

## 3. 术语与缩写

### 3.1 首次出现

面向默认读者时，陌生术语第一次出现应包含：

```text
术语或缩写（全称或中文名：它的含义，以及在当前问题中的角色或影响）
```

例如：

> nDCG（归一化折现累计增益：衡量高相关结果是否排在列表前部）

保留正式术语，方便读者继续搜索；不能只用口语替代术语，也不能只给英文全称而不解释作用。

### 3.2 解释程度

- 解释深度按 §1.2 受众政策表的读者档执行；工程师读者档的通用工程术语不加定义；
- 用户已明确掌握的常用术语可以缩短解释；
- 可独立阅读的章节可以重复一次短定义；
- 一次只引入当前步骤必需的主要概念；
- 相近术语通过职责、输入、输出和所处位置区分，不只给词典定义。

## 4. 项目事实与举例

### 4.1 事实来源

先判断例子要说明哪类事实，再读取对应来源：

- 业务预期和验收：用户最新明确确认；当前需求契约只有在已同步该确认时才等价；
- 实现结构：当前源码和生效配置；
- 测试意图和覆盖范围：测试代码；
- 已验证行为：当前 revision 和适用环境下的实际测试输出；
- 目标运行事实：指定环境、部署或依赖版本和时间窗口下的实际观测；
- 外部依赖行为：已核实且适用于当前版本的权威资料。

不同领域的来源不能互相替代。用户期望不能证明代码已经实现，测试代码不能证明测试已经通过，源码也不能证明目标环境正在运行该版本。旧日志、旧文档和模型记忆只能帮助定位，不能直接裁决当前事实。

### 4.2 例子身份

当例子可能被误认成当前项目事实时，区分以下类型：

| 类型 | 使用条件 | 表达要求 |
|---|---|---|
| 项目实例 | 输入、过程和结果已经核实 | 按需说明来源和适用范围 |
| 项目化简例 | 来自真实流程，但名称、数量、数据或敏感字段已调整 | 准确说明实际简化了什么，不使用固定免责声明 |
| 通用教学例子 | 缺少适用项目事实，或用户询问通用概念 | 说明它是通用示例，不得映射成项目现状 |

### 4.3 例子生成步骤

1. 从真实业务操作、代码、测试或故障中找到原型；
2. 保留角色、触发动作、输入、处理组件、结果和当前要解释的边界；
3. 删除无关实现和敏感信息；
4. 例子可能被误认成项目现状时，说明其通用性质或实际简化内容；
5. 检查数量、名称、顺序、公式输入、输出和结论前后一致；
6. 例子用于支持设计、效果或完成结论时，说明它能证明的范围和不能外推的内容。

### 4.4 禁止事项

- 虚构客户、用户反馈、线上事故、性能数字或测试结果；
- 使用与项目无关的故事，却让读者误以为是项目业务；
- 为了显得生动而改变技术因果关系；
- 用教学数据证明当前系统效果；
- 例子中的数量、列表、公式和结论互相矛盾。

## 5. 代码、命名与注释

### 5.1 代码约定来源

本 Skill 不发明跨语言代码风格。修改前读取格式化配置、静态检查配置、同目录代码和项目规则。

只有当前 owner 已决定创建或重命名标识符时，本 Skill 才检查名称是否表达业务对象或动作；不得仅为改善文字风格主动重命名公共 API、协议字段或兼容接口。`data`、`manager`、`handler`、`process` 等宽泛词只有在项目已有稳定含义时使用。

### 5.2 何时写注释

本 Skill 不要求为了“可读”而增加注释。只有用户要求、项目规范要求，或代码无法直接表达以下信息时才增加：

- 业务原因和不能随意改变的约束；
- 非显然的兼容条件、单位、格式或时序；
- 接口副作用、失败方式或安全边界；
- 看似可以简化但必须保留当前写法的原因；
- 临时方案的退出条件和责任。

### 5.3 注释内容

- 行内注释主要解释“为什么”，不复述下一行代码做了什么；
- API、类、函数文档说明用途、输入、输出、错误、限制和副作用；
- 先改善名称和代码结构，不能用长注释掩盖难读代码；
- 代码变化后同步更新或删除过时注释和已完成 TODO；
- 注释语言服从项目规范，不加入 AI 生成声明或操作旁白。

## 6. 不同文种的组织方式

### 6.1 技术解释

复杂问题按需使用：

1. 直接结论或当前问题；
2. 项目中的实际情况；
3. 组件按什么顺序处理；
4. 对产品、开发或最终用户的影响；
5. 证据、适用范围和未验证部分。

简单问题直接用一到三段回答，不机械增加标题。

### 6.2 操作步骤

- 开头写明完成后的可观察结果；
- 列出真正必要的前置条件；
- 按用户实际操作顺序编号；
- 每个关键步骤给出预期界面、输出或状态；
- 存在已核实、相关且会阻断当前任务的失败方式时，说明处理方法；没有可靠事实时省略，不为凑结构编造故障；
- 当前任务所需步骤写在正文中，不能要求读者打开链接后自行寻找。

### 6.3 代码、公式和图

使用“目的 → 内容 → 结果 → 解释”的顺序：

- 前面说明它回答什么问题；
- 标明代码能否直接运行以及依赖什么；
- 公式解释符号和适用条件；
- 图前说明要观察什么，图后说明关键关系；
- 给出预期输出、代入结果或验证方式；
- 不能用代码块、图标或表格装饰空洞正文。

### 6.4 最终工作汇报

按信息价值组织，不写执行日记：

- **结果**：用户或系统现在有什么可观察变化；
- **实际改动**：涉及哪些文件、模块或行为，以及为什么；
- **验证**：实际执行的命令、测试、检查或观察及结果；
- **限制**：真实存在的未完成、未验证范围和影响。

没有限制时可以省略该节。没有运行验证时不能写“通过”，应说明未验证原因和可执行的验证方法。

## 7. 引用与外部资料

- 先在正文解释事实，再给引用；
- 外部资料只裁决对应依赖、协议或标准，不覆盖项目需求、代码和运行事实；
- 引用易变内容时说明适用版本或日期；
- 不堆链接，不用“详见文档”代替当前任务所需说明；
- 直接引语、具体数字、历史日期和厂商行为应能回到实际来源；
- 路径和行号帮助核对代码，但路径本身不是解释。

## 8. 输出前检查

输出前只检查以下问题，不展示内部检查过程：

1. 默认读者不打开引用能否理解主要结论？
2. 项目判断是否来自当前事实，而不是通用经验？
3. 过程和动作类表述是否写清执行者、动作、对象和结果；定义、状态和约束是否写清含义、条件和影响？
4. 陌生术语第一次出现时是否解释了含义及其在当前问题中的角色或影响？
5. 例子可能被误认成项目现状时是否说明简化或通用性质，数据和结论是否一致？
6. 代码、公式或步骤是否给出可观察结果？
7. 完成、修复和通过等结果声明是否有对应证据？
8. 是否出现 §2.3 禁止的隐喻化工作简称、企业套话或空洞评价；引用错误原词时是否立即给出直白替换？
9. 存在精确标识符时是否写出原名；来源简称缺少实际事实时是否先取证，而不是换成另一个抽象说法？
10. 缺陷与旧行为描述中出现“无法、不能、不可能、永远、根本”时，是否属于 §2.5 允许的原理性限制并在同句给出依据；否则是否已改写为实际行为？

## 9. 测试与增量改进

### 9.1 单次测试记录

用户显式测试本 Skill 时，在当前测试会话中保留以下最小信息；除非用户要求归档，否则不创建测试文档：

- 测试输入和必要项目上下文；
- 实际输出；
- 用户指出的具体问题；
- 用户认可的改写或成功标准；
- 问题属于触发、事实、读者、术语、例子、结构、证据还是语气。

### 9.2 运行态与维护任务

1. 普通调用和测试运行只报告失败、现有规则缺口和候选改法，不修改 Skill 文件。
2. 只有用户明确发起维护本 Skill 的独立写入任务后，负责该任务的 owner 才能修改规则。
3. 一次可复现失败可以修正已有意图的最小缺口；新增适用范围更广的长期规则，需要用户声明为稳定偏好，或提供同类失败重复发生的证据。
4. 跨会话重复只以用户提供的历史反馈或可访问记录为依据，不假设 Skill 记得旧会话。
5. 已有规则覆盖问题时优先澄清触发条件或示例，不重复加规则；每次只补最小缺口。
6. 隐喻化工作简称的候选词只用于扫描和回归，未列出的比喻、自造标签或会话简称仍受 §2.3 硬门禁约束；不能把词表当成允许清单。
7. 规则行为发生变化时同步更新 `SKILL.md` 与 `SPEC.md` 版本；纯澄清升 PATCH，新增规则升 MINOR，破坏触发或边界升 MAJOR。

### 9.3 回归测试

内容规则修改后至少重测：

- 原始失败输入，保留其中已有的“索引风暴、车道、逃生门、速率地板、保险丝、四象限、钉住”等来源措辞，确认输出全部改为具体行为；
- 一个表达不同但问题相同的输入；
- 一个包含精确代码、API 或配置标识符的输入，确认输出写出标识符原名且说明文字仍为直白表达；
- 一个只给出“四象限”等简称、没有列出对应事实的输入，确认输出先取证或标明信息缺失，不换成“四类场景”等另一个抽象说法；
- `fixtures/02-ability-words.md` 的六句输入：四句误用改写为实际行为，两句成立用法保留能力判断并带出依据，正常对照句不被误改；
- 一个原本表现正常的技术解释或最终汇报。

`description` 的触发回归必须在干净会话中通过实际运行时执行，检查应触发和不应触发的输入。环境不支持真实路由时，明确记录“未执行”，只能提交候选测试输入，不能宣称触发验证通过。

§2.3 的通过标准是输出中不存在未获两类可核验例外的隐喻化工作简称或套话，精确标识符已写出原名，来源事实不足时没有换用另一个抽象说法，不能由模型主观判为“可接受”。其他写作质量仍需确认问题不再出现、原有正确行为没有退化；用户审核优先于机械句长评分。
