# 工程写作风格 Skill

**skill_id**: `engineering-writing-style`  
**版本**: 1.1.0  
**output_dir**: `N/A`  
**SPEC**: [SPEC.md](./SPEC.md)

## 1. 完整加载门禁

通过文件工具读取本 Skill 时，必须单独读取 `SKILL.md`，并确认返回结果满足 `start_line=1`、`end_line=total_lines` 且没有截断标记。未读到文件末尾时，从 `end_line + 1` 继续读取；在完整加载前不得执行受本 Skill 约束的写作任务，也不得声称已经读完。

`SPEC.md` 不默认整份读取。先定位章节标题，只加载当前文种和问题需要的细则；任务范围变化时再补读相关章节。

## 2. 目标

让项目中的临时回复、进度说明、TODO、工作日志、代码注释、文档和工作汇报都能被大多数项目同事直接读懂，同时保留必要的技术精度和证据。

默认读者知道项目要解决什么问题，但不了解当前代码结构、算法缩写、内部代号和隐含背景。专业细节可以保留，但必须先解释它在当前项目中做什么。

## 3. 核心规则

1. **先回答问题**：先写当前结论、用户结果或待解决问题，再补充背景；不以行业历史、宏大意义或执行过程开场。
2. **项目事实优先**：先判断结论属于业务预期、代码实现、测试结果还是目标运行，再读取该领域的当前来源；外部资料不能代替项目事实。
3. **正文自包含**：读者不打开链接、不跳转文件也能理解主要结论；引用、路径和链接只负责核对与继续深挖。
4. **禁止隐喻化工作简称**：所有可见输出都不得沿用会话或旧材料中的比喻、自造标签、拟人化简称和形象化代号。存在精确标识符时必须写出标识符原名；其他表达一律改写为主体、触发条件、实际动作和可观察结果。来源简称缺少实际含义时先回到代码、测试或记录取证，不能换一个抽象词继续写。
5. **写清实际关系**：过程说明写清“谁做什么、作用于什么、产生什么结果”；定义、状态和约束说明写清含义、条件及影响，避免用抽象名词和套话隐藏事实。
6. **例子来自事实**：优先从真实业务、代码、测试或故障中裁剪例子；简化或通用示例可能被误认成项目现状时，必须说明实际简化内容。
7. **结论带证据和边界**：完成、修复、效果变化和通过等表述必须说明实际证据、适用范围和未验证内容。

### 3.1 提交信息输出合同

- 使用直接、完整的工程语言；存在代码、API 或配置标识符时写出原名，不用新造的中文简称替代。
- 不沿用工作过程中的比喻、自造标签、拟人化简称、箭头链或未解释缩写。
- 把工作简称改写为“触发条件 + 具体主体 + 实际动作 + 可观察结果”；事实不足时先取证，不用另一个抽象说法代替。
- 只保留会改变评审判断的事实；diff 能直接看出的低层实现不逐项复述。
- 提交信息专用结构仍由 `git-governance` 决定，本合同只约束文字表达。

## 4. 触发与不使用边界

### 4.1 使用场景

- 生成临时回复、进度说明、TODO、任务标题或工作日志；
- 解释项目架构、算法、接口、配置、故障或业务规则；
- 编写或修改用户可见文案和必要注释；
- 当前 owner 已决定创建或重命名标识符，需要检查名称能否准确表达对象或动作；本 Skill 不主动发起重命名；
- 编写需求、设计、README、教程、审查意见、提交信息或 PR 描述；
- 汇报开发、调试、测试、调研或重构结果；
- 用户指出文字空洞、术语过多、缺少项目背景、例子失真或“AI 味”明显；
- 任务进入最终回复阶段，且回复包含项目判断、完成声明或技术解释。

### 4.2 不改写场景

- 用户要求原样输出日志、报错、协议报文、机器 JSON 或精确引文；
- 工具或程序要求固定格式，改写会破坏解析；
- 只返回一个路径、命令、状态值或其他无需解释的短事实。

即使主体内容需要原样保留，主体外的说明仍遵守本 Skill。

## 5. 与其他 Skill 的关系

本 Skill 是表达约束，不拥有任务流程和产物目录。

- 开发、调试、审查、Git、需求和知识沉淀任务仍由对应 Skill 决定流程、结构和退出条件；
- 本 Skill 只检查这些任务产生的文字是否清楚、具体、自包含且有证据；
- 产物 Skill 的专用格式高于本 Skill 的通用结构。例如知识文章可以完整展开，最终工作汇报则先写结果；
- 不把代码架构、测试策略、安全规则或 Git 流程复制到本 Skill。

## 6. 最小执行流程

1. 判断读者要解决什么问题，以及当前产物属于技术解释、操作步骤、代码注释还是结果汇报。
2. 先定位 [SPEC.md](./SPEC.md) 的章节范围，只读取当前文种需要的细则，再读取与结论直接相关的项目事实；不为写得“像项目”而猜测业务。
3. 选择最短的适用结构，不机械创建空章节。
4. 写作时一次引入一个主要概念，术语在第一次需要时解释。
5. 举例时先找真实原型，再删除无关和敏感细节；只有例子可能被误认成项目现状时才标明简化内容或通用性质。
6. 输出前检查事实、数字、名称、输入、过程和结论是否一致，并扫描隐喻化工作简称；命中后必须改成主体、条件、动作和结果。完成声明按项目证据门禁处理。

## 7. 运行态测试与维护边界

用户显式测试本 Skill 时，在当前会话保留测试输入、实际输出、用户指出的问题和认可的改写，默认不另建测试文档。运行态只报告失败、现有规则缺口和候选改法，不修改 Skill 文件。

只有用户明确发起维护本 Skill 的独立写入任务后，负责该任务的 owner 才能按 [SPEC.md](./SPEC.md) 的流程修改规则和版本。一次可复现失败可以修正已有意图的最小缺口；新增宽泛规则需要用户声明为稳定偏好，或提供同类失败重复发生的证据。
