feat(reliability,embedding): 吞吐治理器与车道分离——429 降速续跑,查询不受索引风暴拖累

背景：
- 两个实测痛点(架构分析 2026-08-20):其一,查询嵌入与索引批嵌入共用一个熔断器,大仓索引撞 429 风暴会把正在使用 IDE 的人的检索一起打进词法降级;其二,"熔断即全停"的保守设计让免费档/低配额用户的索引在风暴期吞吐归零,而正确行为是降速贴着配额继续跑。
- 上游过载信号分两类:配额型托管发 429(该学速率——托管服务单请求耗时波动大,固定并发下速率自漂,业界同型=AWS SDK adaptive retry 的客户端令牌桶);容量型自部署只会延迟爬升(该学并发窗口,业界同型=Netflix concurrency-limits 的延迟梯度)。两个控制器同时在线取更紧者,厂商无关性由信号驱动达成。

变更：
- 新增 reliability.Governor:速率控制器(首个 429 前不限速;429 后目标速率乘性减、干净期加性增、尊重 Retry-After 硬暂停、地板=一批的量级)+ 窗口控制器(长短双窗延迟均值偏离 1.5 倍即乘性收窗,每 8 个干净样本加性回升;超时/503 同收窗)。全部常数就地注明出处与理由。
- embedding.Client 车道分离:索引车道与查询车道各持独立熔断;查询直通治理器与并发槽(交互请求一次一条,不排在几十个索引批后面);索引车道每次真实 HTTP 尝试过治理器闸并回报观测。
- 熔断升级路径收紧:索引车道的 429 最终失败在速率未到地板时不再进熔断(治理器已降速),到地板仍被拒才全停——保险丝语义保留为最后防线;认证/额度/永久类错误行为与之前逐字节一致。
- OPENACE_THROUGHPUT_GOVERNOR=off 逃生门:回到共用单熔断+固定并发的旧行为(测试钉住)。
- MaxConcurrency 语义从固定值升级为上限(治理器在 [1,上限] 内寻优);用户 RPM/TPM 预算保持为不可逾越硬顶。指纹:治理器开关是运行时参数不入指纹,指纹版本升 v3(为同批的批车道模式字段腾位,见后续提交)。

影响与边界：
- 索引风暴期:查询照常 hybrid(独立熔断);索引从停摆变为贴配额续跑,fake 配额端到端实测吞吐收敛不归零。
- 自部署:并发窗口按延迟自动收放,固定 16 并发压垮小服务/吃不满大集群的两头问题消解。
- 逃生门 off 时行为与引入前逐字节一致。

Tests: 治理器单测 9 项(AIMD/地板/双窗梯度/阻塞唤醒/取消/nil 直通)+车道隔离 3 项(风暴中查询存活/逃生门旧行为/未到地板不熔断)+引擎级风暴穿越;全量 18 包+reliability/embedding/localengine race 绿
