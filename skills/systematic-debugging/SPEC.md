# 系统化调试 Skill 规范

**版本**: 2.0.2
**适用范围**: systematic-debugging 当前调试事实源、证据表示和声明退出门禁

---

## 1. 目标与边界

本规范只定义调试产物的事实源地位、内容语义、证据表示和退出证据，不重复 SKILL 中的 owner 判定、调查动作、授权或止血流程。

同一故障 scope 同一时点只维护一份当前调试产物。它是故障调查、根因结论、修复授权和 handoff 的当前记录，不覆盖源码、配置、测试、运行结果、外部一手来源或用户动作授权本身的事实权威。

## 2. 事实源与权威

| 领域 | 当前权威来源 |
|---|---|
| 预期业务行为与验收 | 用户最新明确确认、已同步该确认的 requirements 产物或适用业务契约；测试定义不能自行改写业务含义 |
| 仓库实现事实 | 指定 revision/工作树下的源码、配置和测试定义；只能说明该版本的实现，不代表目标环境正在运行它 |
| 目标运行事实 | 指定目标、部署/依赖版本和时间窗口下的实际运行、数据、日志、trace、指标或人工观测 |
| failure oracle 定义与适用边界 | 已同步当前证据的调试产物；每次实际结果仍以对应目标和窗口的真实运行/观测输出为准 |
| 当前根因结论、反证和残余不确定性 | 已同步当前证据的调试产物，且必须可追溯到仓库、运行或外部真实来源 |
| diagnosis/mitigation/repair 动作授权 | 用户当前明确指令或具体动作确认；调试产物只同步记录，不能自行授予或延长权限 |
| 修复实现与验证结果 | 实际仓库 diff、受控系统动作/审计记录、前后状态、测试和运行输出；调试产物负责归档结论与可审计定位 |
| 外部依赖或服务事实 | 实际可访问的一手/权威来源及适用版本/日期 |
| 历史背景 | 旧调试产物、work-log 和旧 review；只作背景，不覆盖当前证据 |

用户最新业务确认或动作授权即时优先，必须在下一次受约束动作前以及退出/handoff 前同步到当前调试产物。SKILL 已批准的紧急处置是唯一首次建档时序例外：具体授权动作完成后立即同步，并在任何后续受约束动作前完成。

不同领域事实源不得互相越权。技术根因结论不要求用户批准才成立，但必须由当前证据支持；用户指令不能把无证据假说变成技术事实，也不能覆盖失败的 oracle 结果。

## 3. 当前产物与更新

固定路径：

```text
docs/debug/YYYY-MM-DD-{scope}.md
```

- `scope` 使用故障现象或受影响能力的 kebab-case 名称；文件名日期是首次建档日期，同一调查跨轮、跨日或跨 owner 恢复时默认更新原文件，不按日期或 mtime 新建“最新”文件；
- 独立故障拥有独立 scope；一个调查中发现另一个无共同 oracle/根因的故障时，拆为另一当前产物并明确交叉证据；
- 确需替代当前文件时，替代文件必须先承接全部仍有效的实质事实和证据，再以明确 `supersedes` 关系原子成为唯一当前源；仅含路径、指针或状态的空壳不得取得权威；
- 恢复时根据 scope、`supersedes` 链和当前证据识别唯一当前源，不按日期/mtime 自动选择。发现竞争源时先收敛现有文件，不创建第三份；
- 产物使用“唯一当前调试汇总产物”表述，不把自身写成覆盖底层证据的唯一事实源。声明不存在竞争产物时，记录实际检查的 scope、候选范围、`supersedes` 关系和结果，不裸写全局唯一结论；
- 取得 owner 后用已有实质事实建档。只在 oracle、证据、假说实验、根因结论、授权、止血、修复、验证、blocker 或 handoff 发生实质变化时更新；不为轮次、尝试次数、等待或状态标签写入；
- 当前技术结论被新证据推翻时，在同一当前产物中保留原结论的证据状态、适用窗口和推翻依据，明确旧证据不再支持哪些当前声明，不回写历史文件伪造当时认知。

## 4. 产物语义

产物按实际存在表达以下语义，不要求固定标题、空栏目或互斥状态枚举：

- 故障现象、可信异常信号和预期行为的事实来源；
- failure oracle、运行/观测方式、适用边界和当前实际结果；
- 已采集且最小化/脱敏的证据及来源；
- 已验证、已推翻和仍待验证的根因假说与实验结果；直接因果证据充分时说明无需额外假说；
- 当前根因结论、直接原因、促成条件、反证和残余不确定性；
- diagnosis-only / repair 授权范围，以及任何需要单独确认的动作；
- 紧急止血的范围、健康验证、风险、回滚、退出条件和清理责任；
- 实际修复、影响范围、原 oracle 与风险回归的实际结果；
- development collaborator 模式下的影响面、经用户审核的 task 及其确认依据、`GATE-SCOPE` 裁决、测试、review、清理和退出门禁证据；
- 临时观测/试验性修改的清理或正式化；
- blocker、残余风险、接收 owner、下一步和 handoff。

只记录可观察事实、可证伪假说、实验和结论，不记录模型私有思维链。

## 5. Oracle 与证据表示

1. 每次支撑 diagnosis、mitigation 或 repair 声明的关键观测都记录通用最小证据包：目标环境与代码/部署/依赖版本、采集时间或窗口、failure/non-failure 判据、关键判别结果、来源/观察者和适用限制。
2. 每项 oracle 判据记录它对应的已确认预期或原始故障症状。与故障同现但尚未成为业务契约或原症状判据的信号只作佐证，不得被写成独立 failure/non-failure 条件。
3. 入口/命令、前置条件、退出码和安全输出位置仅在实际存在且可安全保留时记录；一次性人工观察、历史现场、短期指标窗口或无持久输出时，记录不适用/未保留原因，不为满足格式制造命令或第二文件。
4. 引用源码、配置或测试时使用仓库相对路径和必要定位；引用外部来源时使用去除 userinfo、token、签名参数和敏感路径后的可识别来源，并记录适用版本/日期和获取日期。
5. 脱敏规则适用于产物全部字段和文件名。命令参数、URL、路径、diff、日志、dump、数据和输出只记录足以支持结论的安全摘要；内容哈希和受控位置只能作为附加元数据，不能单独替代证据；受控位置还要记录访问前提、保留/可用性边界，接收 owner 不可访问时说明限制或 blocker。
6. oracle 在调查中确需修订时，说明旧 oracle 为什么不足、新 oracle 如何仍覆盖原始症状；保留修复前基线和关键运行结果，不得删除、弱化或改写失败条件来制造通过。
7. 每个实际存在的假说记录区分性证据，或已执行实验及其实际结果。直接因果证据充分时不要求额外实验；没有充分区分性证据时只保留为候选解释，不写成根因。
8. “未修改”“已清理”“不存在竞争产物”等过程性结论同样属于证据声明；记录实际检查范围和结果，未核验时明确标注，不能用无留痕自述支撑退出门禁。

## 6. Diagnosis、Mitigation、Repair 与 Blocked 表示

这些是可并存的证据声明，不是互斥状态或迁移图；每项只按实际成立范围记录。

- **Diagnosis**：说明根因如何解释 oracle、由什么当前证据支持，以及哪些冲突证据已解释或仍保留；直接原因与促成条件分别记录。
- **Diagnosis-only**：明确未授权的持久修复，以及每项已取得具体授权的诊断动作、作用范围、实际实验和清理结果。
- **Mitigation**：区分计划与实际执行。已执行止血记录获授权动作、作用目标、执行时间、动作后健康验证，以及安全可得时的动作前证据；无法安全采集动作前基线时记录原因、已有异常信号和验证限制。还要记录适用范围、风险、回滚、退出/过期条件、清理 owner 及后续 diagnosis/repair/blocked/handoff 去向，只证明影响受控。
- **Repair**：记录实际仓库变更，或受控系统动作、审计 ID、前后状态等可审计定位，并明确可控致因路径；不可修改的外部根因仍存在时如实保留，只证明本方防护或隔离路径。
- **Blocked**：写明被阻塞的是 oracle 建立、diagnosis、mitigation、repair、repair verification 还是清理；明确完成该声明所缺的证据或动作、实际 blocker 证据、当前为什么不存在安全且已授权的取证或执行路径、解阻责任和可判定重新进入条件。只有 oracle/diagnosis blocked 需要说明为什么没有区分性证据路径；投机路径、假说或实验只在实际存在时记录。

## 7. 退出与 Handoff 证据

### 7.1 Diagnosis-only 完成

必须可观察到：

- 已从本次实际加载的 SKILL source 目录读取同目录 SPEC，当前产物位于固定 `docs/debug/YYYY-MM-DD-{scope}.md`，没有把根目录 `DEBUG.md` 或其他自创路径当作替代当前记录；
- failure oracle 可靠且适用边界明确；
- 根因结论有当前支持证据、可证伪，反证和残余不确定性已表达；
- 没有把未授权修复、mitigation 或候选假说写成完成；
- 临时诊断改动已清理或正式化；
- 当前调试产物已同步；
- 未获用户直接 remediation/修复请求时，没有创建 requirements/development/refactor 产物或展开下游方案；根因明确和含糊的“继续”没有被写成扩权依据。

### 7.2 Repair 完成

除 diagnosis 门禁外，还必须可观察到：

- 实际修复位于授权且可控的 scope；
- 修复针对的可控系统条件或致因路径按假说发生预期变化；外部根因仍存在时明确保留，并验证本方防护/隔离路径；
- 原 failure oracle 已通过，风险相称回归不存在由本修复引入、与修复结论冲突或使授权 scope 不成立的失败；已证实无关的既有失败可以保留，但必须附证据和残余风险；
- 静默 fallback、吞错或 oracle 弱化没有冒充修复；
- 调试产物记录仓库 diff/相对路径，或受控系统动作、审计 ID、前后状态等可审计定位，以及最小证据包和清理。

### 7.3 Mitigation 退出紧急处置步骤

必须可观察到：

- 实际动作获得授权，并有作用目标、执行时间和可审计定位；
- 动作后影响控制/健康 oracle 证明止血目标达到；动作前证据在安全可得时记录，未采集时说明原因和验证限制；
- 适用范围、风险、回滚、退出/过期条件和清理 owner 明确；
- 后续 diagnosis、repair、blocked 或 handoff 去向明确；
- mitigation 证据没有外推根因或永久修复完成。

### 7.4 Blocked

必须可观察到：

- 当前调试产物存在且包含已有实质证据；
- 被阻塞的声明范围和实际 blocker 证据明确；
- 已说明完成被阻塞声明所缺的证据或动作，以及为什么当前没有安全、获授权的取证或执行路径；oracle/diagnosis blocked 额外说明为什么没有区分性证据路径；
- 解阻责任和可判定重新进入条件明确；
- 没有无证据的确定根因或修复声明；
- 临时改动已清理/正式化，或记录遗留、风险、责任和处理条件。

### 7.5 Owner 后的 Handoff

必须可观察到：

- 存在用户直接提出的新目标或动作授权；根因明确、Agent 主动建议或含糊的“继续/continue”不能单独构成 handoff 依据；
- 精确当前调试产物路径、接收 owner 和下一步；
- oracle、授权范围、有效证据、实际存在的假说/实验、已做止血或修复、残余风险和验证边界按实际提供；
- 正常 handoff 不制造 blocker；blocked handoff 额外引用 blocker 证据；
- 不适用项省略，不填空栏目；
- 临时改动已清理/正式化，或明确遗留责任；
- 已授权的中高风险仓库内 repair 使用 development collaborator 时，当前 debug 产物已承接进入、task 审核、执行和退出证据，`docs/development/` 不作为进入前置或第二主记录。

`GATE-EVIDENCE` 分别证明 diagnosis、mitigation 和 repair 成功声明；一类证据成立不得外推其他结论。Blocked/handoff 由本节专用门禁和 `GATE-SOURCE` 证明其范围、blocker、接收方与下一步真实存在，不把它们解释为成功声明或强制执行不适用验证。

## 8. 读取方式

1. SKILL 已先完成 owner 复核；不拥有时不读取本文件。
2. 取得 owner 后，以 loader 报告或本次实际读取目标中的 SKILL source path 为基准，读取同目录 `SPEC.md`；不得按任务 cwd、项目根或同名搜索结果解析 `./SPEC.md`。
3. 本文件实际读取成功后，才枚举同 scope 候选并按第 3 节选定或创建唯一当前产物；不得用 `DEBUG.md`、工作日志或其他自定义路径替代固定 `docs/debug/` 产物。
4. 无法确定 source path 或读取本文件时，停止并报告 load blocker，不得把“项目内没有 SPEC”写成继续执行或完成依据。
5. SKILL 允许先行的紧急处置完成后，必须立即按同一 source path 读取本文件、识别当前产物并补记实际事实。
6. 当前工具只能整文件读取时，如实加载完整 SPEC。
7. 评测语料、hidden cases、grader 和客户端 fixture 不进入运行时 SKILL/SPEC。

## 9. 版本历史

| 版本 | 变更 |
|---|---|
| 2.0.2 | 明确 `SPEC.md` 必须相对实际 Skill source path 加载，不得相对任务 cwd 查找；禁止用根目录 `DEBUG.md` 或自定义路径替代固定 debug 产物，并将加载/路径纳入退出门禁 |
| 2.0.1 | 明确 diagnosis-only 完成后停止；根因明确不自动授权下游规划或 handoff；含糊的“继续/continue”继承当前 scope，不得扩权创建 requirements/development/refactor 产物 |
| 2.0.0 | 收窄未知根因 owner；以可靠 failure oracle 取代稳定复现绝对要求；扩展非源码根因、diagnosis-only、紧急止血、blocked、授权和 development collaborator 边界；建立唯一当前调试事实源、分域事实权威、证据包及按声明类型区分的退出/handoff 门禁 |
| 1.1.0 | 对齐 AGENTS 完成前证据门禁与项目根规则，补充 pua 失败恢复协同 |
| 1.0.0 | 初始版本，定义固定复现、定位、修复和验证流程 |
